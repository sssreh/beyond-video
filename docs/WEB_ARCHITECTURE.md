# bv-web architecture (side project)

`bv-web` is a small, separate side project from the main `bv-*` pipeline documented in `docs/ARCHITECTURE.md`: a login-protected web app for *browsing and watching* trips the pipeline's `bv-export` step already produced. It doesn't download from a camera and doesn't generate anything - but it does read the raw source archive too, via the archive browser (see "Archive browser" below), in addition to `bv-export --target`'s own output folders. That means it needs both `data/trips` and `data/archive` mounted in deployment (see "Deployment" below) - an easy thing to miss since only the trips mount was needed in this project's earlier increments. For the one piece that crosses over between the two projects, see "Relationship to bv-live" below.

## Why it's a separate project, not a feature of the pipeline

The pipeline (`bv-config` through `bv-export`, plus `bv-live`) is built to be run by one person, from their own machine, with no login at all. `bv-web` exists for a different situation entirely: letting other people - family members, say - see trips after the fact, from a browser, without shell access to the machine that ran the pipeline. That needs accounts, roles, and sessions, none of which the rest of the project has any use for - keeping it a separate top-level package (`blackvue.web`, not folded into `blackvue.export`/`blackvue.cli`) means none of that login machinery leaks into tools that were never meant to need it.

It also has its own, heavier optional-dependency group (`fastapi`, `uvicorn`, `python-multipart`, `Jinja2` - see `pyproject.toml`'s `web` extra) and, in deployment, its own Docker image (`Dockerfile`) separate from the pipeline's own (`Dockerfile.cli`) - see "Deployment" below.

## What it does today

Started as deliberately browse/watch only; later increments (below) added the ability for the owner to trigger every `bv-*` pipeline command - `bv-config`, `bv-gps`, `bv-download`, `bv-generate`, `bv-export`, and `bv-ls` - from the browser. `bv-ls` was the last one wired in, and also the odd one out chronologically: it's the very first `bv-*` command this project ever had, overlooked in every earlier round of "wire the pipeline into the browser" until Christer pointed out the gap. See "Job runner" below for its own design notes.

- **Login** - username/password, session cookie. Two roles: `owner` (currently just Christer) and `viewer` (everyone else). Browsing/watching trips and the raw archive works the same for both roles; triggering a job (below) is `owner`-only.
- **Welcome page** (`GET /`) - the actual post-login landing page, added after Christer's own feedback that trips shouldn't be the first thing a user sees: "I don't think we should start with trips after login, yes trips are the end goal, but not the starting." A short "Welcome to Beyond Video" heading/summary plus a `Home`/`Trips`/`Browse archive` (and, for the owner, every job-trigger) quick-link grid - `welcome.html`, gated by `require_login` like everything else here, not `require_owner`, since a viewer should land somewhere too, not just the owner. This page also turns its own background tint *and* blur off entirely (`.page-tint--none`/`.page-bg--sharp`, see "Theme" below) - Christer's own suggestion, "we could also make the background totally untinted for this page" - rather than reusing the same dark, blurred backdrop every other page keeps for legibility over its own denser table/panel content. The blur turned out to matter as much as the tint: an initial tint-only version still "look[ed] tinted" to Christer even with the dark wash genuinely off, because `.page-bg`'s existing `filter: blur(18px)` alone was already enough to read as flat/washed-out - see "Theme" below for both overrides together.
- **Trip list** (`GET /trips`, moved off `GET /` for the welcome page above) - every trip found by `scan_all_trips()` (`web/trips.py`), scanned fresh on every request (not cached), so a trip `bv-export` finishes writing while `bv-web` is already running shows up without a restart. Task #762 traces the design history here: `bv-config`'s own wizard suggests each camera's Target as a sibling-of-Archive subfolder nested by camera id (`.../trips/<camera-id>`, see `default_target_dir()`), while `bv-web serve`'s positional `TARGET` only ever names one directory - Christer, once that mismatch was pointed out: "Thats a dilemma." A first fix (task #756) had `scan_trips()` recurse one level into non-trip subfolders of that single shared directory - handled the common wizard-default layout, but not the fully general case: "Of corse every Camera should have the option to put trips where ever it wants. At the same time bv-web needs to see them all." `scan_all_trips(config_dir, fallback_target)` (task #763-769) replaces that recursion trick: it reads every configured camera's own `CameraConfig.target` (via `list_camera_ids()`/`load_camera_config()`, same `default_config_dir()` `_camera_options()` already uses) and scans each one directly with `scan_trips()`, re-identifying results as `"<camera-id>/<trip-folder>"`; `fallback_target` (bv-web's own `TARGET` argument, unchanged in the CLI) is still scanned flat, for cameras with no configured Target or trips exported with an explicit `bv-export --target` override, and results are deduped by resolved folder path. `scan_trips()` itself went back to a flat, single-level scan - the one-level-recursion trick is gone, so a two-segment trip id has exactly one meaning app-wide: "camera_id/trip_folder", resolved through that camera's own config (see `_find_trip()`/`_resolve_camera_target()` below), never a directory-tree guess. `bv-export` itself warns ("you're on your own trip") when an explicit `--target` diverges from the camera's own configured default, since that trip will only ever show up via the flat fallback path, not the per-camera one.
- **Trip detail** - video playback (range-request support comes for free from Starlette's own `FileResponse`, so seeking/scrubbing works), plus GPX/SRT download links, whichever of those a given trip actually has (a trip only has the files the `bv-export` run that produced it actually asked for - no `map.mp4` without `--map`, etc.). A video player issues one HTTP request per range while seeking/buffering, and each one resolves the same `trip_id` again - `trips.TripCache` (a small per-trip, short-TTL cache, default 2 seconds) sits behind that resolution so a burst of range requests from one seek/buffer event collapses into a single real `scan_trip()` call instead of repeating its ~nine stat()/open() calls every time. Deliberately scoped to this single-trip lookup only - the trip list below still scans fresh on every request, unaffected.
- **Archive browser** - the raw per-camera archive `bv-download` actually writes to disk, before `bv-export` groups anything into trips: a camera picker, a day-grouped thumbnail grid per camera, and a per-recording detail page. See "Archive browser" below for how.
- **Jobs (owner-only, except bv-search)** - the owner can trigger `bv-config` (set up or edit a camera), `bv-gps` (get a live GPS fix, against an already-configured camera id only, optionally with `--snap` to also grab a per-direction camera snapshot - see "Inline snapshot preview" below), `bv-download` (download recordings from the camera into its archive), `bv-generate` (extract audio/duration/transcript/translation for a camera's archive), `bv-export` (detect trips and export them), `bv-ls` (print a camera's archive as a compact table, or one row per detected trip), or `bv-scribe` (describe scenes and/or read visible text via a vision-language model) as a background job from the browser, watch its output, answer `bv-config`'s wizard questions as they come up, and cancel a job that's running or stuck. `bv-search` (search transcripts/translations/scene descriptions by text and/or GPS proximity) is the one job type any logged-in viewer can trigger too, not just the owner - see "Job runner" below for how and why.
- **Theme** - a manual light/dark toggle (a `bv_theme` cookie, read directly in `base.html` via `request.cookies` rather than every route threading a theme variable through its own `TemplateResponse` context), and a full-app background image behind every page: two fixed, full-viewport layers (`.page-bg` - the theme's own photo, blurred; `.page-tint` - a flat wash of the theme's `--bg` color at partial opacity over it) sit behind the real page content (now a `.page-shell` div, not `<body>` itself), swapped per-theme the same way every other CSS custom property in `base.html` is. Christer's own two derived aerial-city renders (see `WORKING_CONTEXT.md` for how the dark one was color-remapped from the light one specifically, to keep them a true matched pair) - shipped as `web/static/backgrounds/bg-light.jpg`/`bg-dark.jpg`, served through a plain unauthenticated `StaticFiles` mount at `/static` (cosmetic images, not trip data, so no login check needed - unlike every other file-serving route in this app). `.page-tint` also has a per-page opt-out: `base.html`'s tint `<div>` reads its class from a `{% block page_tint_class %}{% endblock %}`, empty by default, so every existing template's tint is untouched; `welcome.html` overrides it (`page_tint_class` -> `page-tint--none`, a plain `opacity: 0`) to show the background photo at full strength on the page that wants it. Not a reusable opacity variable - there's only a couple of pages that need this today, and "off" is a much simpler thing to reason about than "some other number." `.page-bg` got the identical treatment for the same reason, one round later: turning the tint off wasn't actually enough on its own - Christer's "It look tinted to me" after seeing the first version turned out to be the `18px` blur itself reading as flat/washed-out with no color overlay left to blame it on. `{% block page_bg_class %}{% endblock %}` -> `page-bg--sharp` (`filter: none; transform: none` - the `scale(1.1)` only ever existed to hide the blur's own edge fringe, so it drops too) is `welcome.html`'s second override. `login.html` followed the same route right after, per Christer's "the login page should also have an untinted background" - it fills the identical `page_bg_class`/`page_tint_class` blocks welcome.html does.

**Legibility over an untinted photo went through three attempts before it actually worked.** Losing both the tint and the blur left the header title, nav tabs, `welcome.html`'s hero heading/summary, and `login.html`'s field labels sitting directly on a genuinely busy photo (dense rooftops/streets, high-frequency detail everywhere) with nothing behind them - first tried a `text-shadow` on the hero copy alone, then extended and strengthened the same shadow to cover the header/tabs/labels too via a `.page-tint--none ~ .page-shell ...` sibling-combinator selector (scoped so it only ever fires on a page that's turned its own tint off). Both rounds still came back from Christer as genuinely hard to read, screenshot in hand each time - a shadow's small blur radius just can't guarantee contrast against real photographic detail the way it can against a flat color; it wins locally, not everywhere text might land. The actual fix: give the header, `.tabs`, `.login-box`, `welcome.html`'s hero card, and its `.quick-links-group-label` chips a small translucent surface to sit on instead - `background: rgba(var(--bg-rgb), 0.78)` plus `backdrop-filter: blur(14px)` (a frosted-glass panel, the same idea a native app's floating toolbar uses over content), replacing the shadow rules entirely rather than stacking on top of them. Deliberately not the same thing as the page-wide `.page-tint` Christer asked to remove: the tint washed the *entire* photo at all times; these panels cover only the handful of small regions that actually hold text (a toolbar strip, a couple of cards), leaving the rest of the photo - most of the page - fully exposed at full clarity. Still scoped through the same `.page-tint--none ~ .page-shell` sibling combinator, so it only ever applies to a page that's opted into the untinted background; every other page's header/nav/panels are completely untouched.

## Archive browser

Trips only exist once `bv-export` has processed them; the archive browser shows what's on disk before that - every raw recording `bv-download` has already saved for a camera, with a thumbnail per recording so a long archive is easy to scan visually. `web/archive_browser.py` (`ArchiveRecording`, `scan_archive()`, `find_recording()`, `group_by_day()`) is deliberately thin, the same way `trips.py` is thin: it reuses `blackvue.archive.Archive`/`ArchiveReader` - the exact same reader `bv-ls`/`bv-export` already use to enumerate recordings from a flat, unstructured archive directory - rather than adding any new disk-scanning logic of its own.

A camera id in a URL (`/archive/{camera_id}`) is resolved to its archive directory via `CameraConfig.archive` - the directory `bv-download` writes raw recordings to. This is a different directory from `bv-export --target`/`app.state.target` (the trips directory `trips.py` reads) - a camera id names a *source* archive, a trip id names *processed* output. Don't confuse the two; `app.py`'s `_find_camera_archive()` helper is the only place this resolution happens, precisely to avoid that mix-up spreading across routes.

The camera list (`/archive`) reuses `_camera_options()` - the same pick-list `bv-config`/`bv-gps`'s job forms already build (see "Camera pick-list" below). The per-camera page (`/archive/{camera_id}`) groups recordings by calendar day, newest day and newest recording first, and shows each recording's thumbnail if it has one - real `.thm` files `bv-download` already downloads (see the sidecar-probing feature in `WORKING_CONTEXT.md`), preferring front, then rear, then interior. A recording with no thumbnail at all (an older archive, or a camera/firmware that doesn't serve `.thm` files) shows a plain "No thumbnail" placeholder instead of breaking the grid - thumbnail presence was never guaranteed, and there's no ffmpeg-based thumbnail generation anywhere in this project to fall back to. The detail page (`/archive/{camera_id}/{recording_id}`) plays the recording's best available video and links every video file it actually has (front/rear/interior). It doesn't link the GPS/g-sensor sidecar files - `.gps`/`.3gf` have no browser-recognized MIME type, so `FileResponse` would just trigger a download rather than displaying anything, and Christer didn't want them shown at all. `ArchiveRecording.sidecars`/`has_gps`/`has_gsensor` still exist on the model (and are still tested) for any future caller that wants them; the detail template simply doesn't render that loop.

**"View this recording in bv-stats" link.** Christer: "from bv-web archive browser i would like a link to bv-stats with a prefilled full timestamp and camera." `ArchiveRecording.stats_timestamp` (`web/archive_browser.py`) strips the trailing kind letter off a recording's own id (`"20260715_140212_N"` -> `"20260715_140212"`) - `LexicalTimeParser._expand()` rejects more than one `_` in a `--timestamp` value, and a raw recording id has two (one before the time, one before the kind letter), so the bare id can't be passed to `/stats?timestamp=` directly; this is the same `rsplit("_", 1)[0]` stripping `TimeInterval.__contains__` itself already applies internally when checking a recording id against a parsed interval. `archive_recording_detail.html` links to `/stats?id={camera_id}&timestamp={stats_timestamp}&group=recording` - the camera preselected, the timestamp narrowed to the exact second this one recording started, and `group=recording` (see "Per-recording (ungrouped) charting" above) so the dashboard lands showing that one recording's own bucket rather than a calendar rollup it'd otherwise disappear into.

**Scene/OCR text panel (task #681).** Unlike the GPS/g-sensor sidecars above, `.scene.txt`/`.rear.scene.txt` - the text `bv-generate --describe-scene`/`bv-scribe` write per recording - *is* rendered directly on the detail page, since Christer's own framing was the opposite of the GPS case: "the only way to read a scene description is opening the file directly on disk." `ArchiveRecording.scene_texts` (`web/archive_browser.py`) iterates the same front/rear `Asset` pair `blackvue/search.py`'s own `TEXT_SEARCH_ASSETS["scene"]` group already searches (`Asset.SCENE_DESCRIPTION`, `Asset.SCENE_DESCRIPTION_REAR`), reads whichever file(s) exist via `Recording.file()`, and returns a `list[(direction label, text)]` - empty for the common case where no `bv-generate --describe-scene`/`bv-scribe` run has happened yet against that recording, so `archive_recording_detail.html` only shows the panel when there's something to show. A read failure (e.g. a permissions problem) falls back to a bracketed placeholder string rather than raising, consistent with this page's existing don't-500-on-a-sidecar-glitch posture.

**Scene summary (cleaner description + legible-only signs).** A follow-up to the panel above: Christer, after a conversation about how much of a real `scene.txt` is `"not legible"` noise (a detected sign/plate crop the model genuinely couldn't read - see `generate/scene.py`'s `zoom_into_signs()`), landed on "maybe i just want a report on the scene files for human reading" -> "like a trip-summary but per recording, could be shown when you look at a video... only freshly generated and not a new file." `ArchiveRecording.scene_summary` (`web/archive_browser.py`) parses each `scene_texts` entry into `(direction label, description, legible sign reads)`: the description comes straight from `blackvue.generate.scene.extract_description_section()` (already used by `--trip-summary`), and legible reads come from a new local `_extract_legible_sign_reads()` that walks the `## Zoomed sign reads` bullet section and keeps only lines whose read text doesn't contain `"not legible"` - stopping at the next `#` heading or the disclaimer footer's `---` divider so `describe_scene()`'s always-appended `DISCLAIMER` (which starts with `---`, not `#`) is never swallowed as more bullets. A direction with neither a description nor a single legible read (e.g. a `--camera both` rear pass, forced to `task="ocr"` with nothing legible in it) is dropped entirely rather than shown empty. Computed live on every request straight from the same files `scene_texts` already reads - no new asset file is written, and unlike `--trip-summary` this never calls the vision model again. `archive_recording_detail.html` shows this "Scene summary" panel above the existing full-text dump, which stays in place (now headed "Full scene text (raw)") for anyone who wants the raw `on-screen-text`/`not legible` detail.

A single zoomed-sign bullet's read text can itself span multiple raw lines - `zoom_into_signs()` writes the model's read text verbatim after the `"- [t=...] {label}: "` prefix, and a multi-row sign (several destinations stacked on one board) comes back with embedded newlines. The first version of `_extract_legible_sign_reads()` only kept the `"- [t=...]"` line itself and silently dropped every continuation line below it - caught by Christer against a real scene.txt where a Swedish road sign's second/third/fourth lines ("259 HUDDINGE" / "JORDBRO" / "500") vanished from the summary entirely, leaving just the sign's first line. Fixed by folding any non-bullet, non-blank line encountered inside the section into the read currently being built (joined with a space) until the next `"- "` bullet or the section's end closes it off.

**Natural-language sign-read timestamps + `scene.srt` download.** `_extract_legible_sign_reads()`'s raw `"[t=60.1s] ..."` bracket notation - both shown on the page and read aloud verbatim by TTS - came out as awkward literal speech ("bracket t equals sixty point one s bracket"); Christer: "instead of trying to say "[t=60.1s]" it would be much better to say "At 60 seconds"  rounded of to closest second." The parsing logic moved into `_parse_sign_reads()`, returning a `SignRead(timestamp_seconds, text)` dataclass whose `display_text` property formats `"At {round(seconds)} second(s), {text}"`; `_extract_legible_sign_reads()` is now a thin wrapper over it, so both the on-page list and the TTS narration picked up the new wording for free. Only the sign-reads sub-pass has real per-frame timing at all - `describe_scene()`'s main narrative feeds the whole video as one inference call with no internal timestamps - which directly answered the other half of Christer's request ("Does the scene detection ever have the timestamps for the description, then i would like a scene.srt file to"): `build_sign_read_srt()` reuses the same parsed `SignRead`s plus `generate/subtitles.py`'s existing `SpeechSegment`/`format_srt()` to build a 3-second-per-cue `.srt`, clamping each cue's start to at least the previous cue's end so cues never overlap. `ArchiveRecording.sign_read_srt(direction)` and a new `GET /archive/{camera_id}/{recording_id}/scene.srt?direction=front|rear` route (modeled on `/trips/{trip_id}/kml` - dynamic generation, nothing persisted, 404 instead of an empty file) expose it; a "Download {label} sign reads as .srt" link sits under each direction's sign-read list, meant for importing alongside that direction's video in an editor so a caption appears at the exact moment each sign/plate was actually detected. `display_text` picked up a follow-up (Christer: "it ok to include minutes to if timestamp > 60 secods") - past 59 seconds it now speaks whole minutes plus any remainder ("At 1 minute 30 seconds", "At 2 minutes" when the remainder rounds to 0) instead of a bare seconds count.

**Video-synced `description.srt` download.** A second .srt sits alongside `scene.srt`, this one for the main `## Description` paragraph rather than the sign reads - Christer, same message as the minutes follow-up above: "Could i also get a srt file that is synced with the video of 3minutes." Unlike the sign reads, `describe_scene()`'s main pass originally had no internal timing at all to sync against (confirmed, not assumed - it was one multi-frame inference call over the whole video producing one holistic paragraph), so the first version of `_chunk_description_text()` split the description into short (~90-char, sentence-boundary-preferred, word-boundary-fallback) chunks - mirroring, without sharing code with, `archive_recording_detail.html`'s own client-side `buildSrtCues()` used for the ElevenLabs-narration SRT - and `build_description_srt()` spaced those chunks evenly across the recording's real elapsed time (from `generate/media.py`'s `load_or_compute_duration()`, the same self-healing `.duration.txt` cache the rest of the pipeline already treats as the source of truth for a recording's length). `ArchiveRecording.description_srt(direction)` and `GET /archive/{camera_id}/{recording_id}/description.srt?direction=front|rear` follow the identical dynamic-generation/404-on-nothing-to-build pattern as `scene.srt`; a "Download {label} description as .srt (video-synced)" link sits under each direction's description text, worded to distinguish it from the ElevenLabs "Download SRT" button just above (narration-timed, not video-timed).

That evenly-spaced chunking was always a stand-in for real per-event timing. Christer: "It would have been nice to both say and subtitle 'To the left, there's a red bus passing alongside the vehicle' at the same time you can see the red buss pass", then confirmed building it with "yes, but please keep the old output and create a scene.srt file too." `DESCRIBE_PROMPT` (`generate/scene.py`) now asks the vision model for bulleted, per-event-timestamped lines for video clips (`- [t=12.4s] A red bus passes on the left...`), leaning on Qwen2.5-VL/Qwen3-VL's temporal grounding since `describe_scene()` already passes `fps`/`max_frames`/`return_video_kwargs=True` into the inference call; still photos keep the old plain-sentence response. `extract_description_section()` (the "keep the old output" half) now parses any bulleted events back out and joins their text into the same clean bracket-free prose every existing caller - trip-summary export, on-page description, TTS narration - already expects, falling back to the raw text unchanged for old-format scene.txt or a still photo's single sentence; a new `extract_description_events()` exposes the structured `DescriptionEvent(timestamp_seconds, text)` list for callers that want real timing. `description_srt()` now tries `extract_description_events()` -> `build_description_srt_from_events(events, duration_seconds)` first (sorts by timestamp, clamps each cue to `[cursor, duration_seconds]`, drops any cue that collapses to zero/negative length), and only falls back to the original evenly-spaced chunking path when no events are found or the events-based build collapses to nothing - so an old-format `scene.txt` (or a still photo) produces identical output to before this change, while a freshly generated one gets captions that actually land when the described event happens on screen.

Two file-serving routes (`/archive/{camera_id}/{recording_id}/thumbnail/{direction}`, `/archive/{camera_id}/{recording_id}/files/{filename}`) follow the same allow-list pattern `trips.py`'s `trip_file` route already established: `ArchiveRecording.known_filenames` is the frozenset of real filenames a recording actually owns, checked before ever touching the filesystem, and `camera_id`/`recording_id` path segments are rejected outright if they contain `/`, `\`, or a `.`/`..` segment - the same guard `_find_trip()` applies to `trip_id` (except `trip_id` itself is allowed exactly one internal `/`, for the `"camera_id/trip_folder"` id `scan_all_trips()` builds, described in "Trip list" above - each of its two segments still goes through the same no-dots check, and the camera segment is resolved to a Target directory via `_resolve_camera_target()` rather than joined onto a single shared path).

**Per-recording lookups don't scan the whole archive.** `find_recording()` is called once per thumbnail on the grid page and once per HTTP range request a video player makes while seeking/buffering - both happen many times per page view/playback session. It resolves a recording via `ArchiveReader.read_recording()` (a targeted glob for just that recording id's own files) rather than `scan_archive()`'s full directory read, which would otherwise stat() every file across the whole archive on every single one of those calls - an N-thumbnail page load would be O(N^2), and a video player would re-scan the whole archive on every range request, which is exactly what made both feel slow/hung on a real archive with hundreds of recordings. `scan_archive()` itself (used once per page load, to build the day-grouped grid) is still a full read - that's a single, unavoidable O(archive size) cost per page, not per recording.

**Filtering** (mode + lexical time range): a long archive can have thousands of recordings, so `/archive/{camera_id}` also accepts filter query params - `mode` (repeatable, N/E/M/P/A), plus `timestamp`/`from`/`until`. The time filter reuses `LexicalTimeParser`/`TimeInterval` from `lexicaltimeparser.py` - the same lexical-prefix matcher `bv-ls`/`bv-export`/`bv-download`/`bv-generate` already filter recordings with on the CLI side (a prefix like `2026`, `20260715`, or `20260715_14` expands to an inclusive range; `--timestamp` can't be combined with `--from`/`--until`). `archive_browser.filter_recordings()` applies both filters together over an already-scanned list; `kind_options()` is the canonical N/E/M/P/A list the filter bar's checkboxes are built from. No mode checked means no mode filter (show every kind) - `app.py`'s route turns an empty checkbox selection into `modes=None` rather than `modes=set()`, since the latter would mean "match nothing." A bad/conflicting time filter shows the unfiltered list plus an error message rather than a 500 or a silently-ignored filter. The filter bar is a plain `GET` form (bookmarkable/shareable URL, no JS) rendered above the thumbnail grid on `archive_recording_list.html`.

Access is `require_login` (any logged-in user), the same as trip browsing - not `require_owner` like the job-trigger routes. No caching here: every request rescans the archive directory fresh (unlike `trips.py`'s single-trip lookup, which now goes through `TripCache` - see "Trip detail" above; the two aren't the same shape of problem - the archive browser was fixed by *avoiding* a full-archive scan per request via a targeted lookup, since scanning here really does mean touching every recording; `trips.py`'s `scan_trip()` was already a targeted single-folder read, just an uncached one, since there's no full-directory cost to avoid in the first place).

**Parking-mode video playback.** Every Parking (`P`) recording's own MP4 fails ffmpeg's/browsers' strict container validation outright ("contradictionary STSC and STCO" - a known BlackVue quirk, not per-file corruption; see `WORKING_CONTEXT.md`'s "Correction: the ffprobe failures aren't per-file corruption" entry), which used to make these recordings silently fail to play in the archive browser's `<video>` tag - Christer's own report: "bv-web can't play parking videos, probably because it's a timelapse video." Root cause turned out to be narrower than the timelapse frame rate: confirmed against one of Christer's own real recordings (via `scripts/dump_parking_container.py`) that the video track's own sample tables are completely intact, and the fault is an empty, vestigial audio track (zero samples, zero chunks, but a stray table entry anyway) - exactly the shape `generate/mp4_box_reader.py`'s own docstring had already theorized. `generate/mp4_repair.py`'s `repair_parking_container()` drops just that one broken audio track from a copy of the file's `moov` box, leaving the video track and all of `mdat` (the real frame data) byte-for-byte untouched; `load_or_repair_parking_video()` wraps it in the same load-if-cached-else-compute-and-cache pattern as the OSM road/geocode caches, writing repaired copies under `default_config_dir() / ".parking_repair_cache"` (bv-web's own writable scratch space, not the archive itself, for the same read-only-mount reason the geocode cache moved there - see "Fix geocode cache dir" in `WORKING_CONTEXT.md`). The `/archive/{camera_id}/{recording_id}/files/{filename}` route swaps in the repaired copy transparently for a Parking recording's own video files only, falling back to the original file unchanged for anything outside that one confirmed, narrow pattern - no template or URL changes needed, since the `<video>` tag's `src` never changes.

## Stats dashboard

`GET /stats` is a browser front end over `blackvue.stats_report` - the exact same aggregation module `bv-stats` (the CLI, `docs/man/bv-stats.md`) is built on, per that module's own docstring: "so a future bv-web stats tab can call the aggregation directly instead of parsing this command's text output." Like the archive browser, it's a plain `GET` form with query-string filters (camera id, `--group` equivalent, `--fields`, `--timestamp`/`--from`/`--until`, `--estimate-gaps`) - no `JobRunner` involved, since aggregating already-computed `RECORDING_STATS` (`<id>.stats.json`, written by `bv-generate --stats`) is a fast read, not a subprocess. `stats_dashboard()` in `app.py` mirrors `bv_stats.py`'s own `_run()`: resolve the camera archive, filter recordings by `LexicalTimeParser`, call `load_recording_stats()` per recording, then `aggregate_recording_stats()` for the grouped buckets and (when the grouping isn't already `all`) a second `grouping="all"` call for the summary section - the same "grand total alongside a grouped breakdown" `--summary` gives the CLI.

Access is `require_login` (any logged-in user, like trip/archive browsing) - a driving-history summary isn't job-trigger-sensitive the way running a pipeline command is, so it isn't `require_owner`-gated.

Five small pieces of query-string/render logic were pulled out of the route into plain module-level functions - `_selected_stat_fields()` (drops any `?fields=` value that isn't a real `STAT_FIELDS` key, falling back to `bv-stats`' own `DEFAULT_FIELDS`), `_selected_graph_fields()` (same validation for `?graph_fields=`, independent of `_selected_stat_fields()` - see "Per-series y-axis scaling" below for why), `_fields_for_aggregation()` (the union of both, since a graph-only field still needs real aggregated data), `_stats_chart_series()` (the `{keys, recording_counts, series}` payload the page's chart script needs, one `values` array per graphed field rather than the whole `StatBucket`), and `_slugify()` (bucket key -> safe HTML element id) - specifically so they're unit-testable the same way `test_app_reuse.py`'s existing helpers are, without a `TestClient` (see that file's own module docstring for why this repo tests `app.py` logic as plain functions). `_slugify` and a `stat_value` filter (wrapping `bv_stats.py`'s own `_format_value()`, so the web page renders every field - duration as `H:MM:SS`, everything else fixed-precision plus unit - exactly the way the CLI report does) are both registered as Jinja filters in `create_app()`.

The chart itself (`templates/stats.html`) is a hand-rolled inline SVG bar/line chart with a vanilla-JS `<script>` - confirmed via a repo-wide grep that no charting library (Chart.js, Plotly, etc.) is used anywhere else in `bv-web`, so pulling one in for a single page would be the only place in the app depending on an external JS charting dependency; staying consistent with the rest of the app's self-contained-template convention won out over the smaller amount of code a library would have saved. Hovering a bar/point shows a tooltip (series label, value, unit, recording count); clicking one scrolls to and briefly highlights that bucket's row in the table below - the "clickable points for actual data" piece of the original request, wired to the same per-bucket recording list (`<details>`/`<summary>` with `/archive/{camera_id}/{recording_id}` links) the table row already shows, rather than reconstructing a time-range URL (which the `weekday`/`monthday` groupings in particular have no single clean range for, since they recur across the whole selection rather than partitioning it - see `stats_report.py`'s own docstring on those groupings).

**Multi-series charting + legend (Christer's own follow-up, 2026-08-23): "I will also like to have more than 1 stats on the y axis and where are my legends."** The original version could only ever graph one field at a time (a single `<select name="graph_field">`) with one hardcoded legend line. The form's "Graph fields" section is now a checkbox group and `graph_fields` is a `list[str]` query param. The chart script draws one colored series per checked field - grouped bars per bucket for the bar chart, one polyline+points per field for the line chart. Bar/line/point colors come from a fixed six-color palette (cycled if more fields are graphed than colors) set inline per-series via JS `setAttribute('fill'/'stroke', ...)`, rather than the single `--link`-themed CSS class every series used to share - `base.html`'s `.stats-chart-bar`/`.stats-chart-line`/`.stats-chart-point` rules now only carry non-color, structural properties (cursor, hover opacity, stroke-width). The legend (`#stats-legend`, still an empty `<div>` in the template) is built entirely from the same `series` payload by the chart script itself - one `.stats-legend-item` (colored swatch + field label + unit + observed min-max range) per graphed field - so it can never drift out of sync with what's actually drawn, unlike the old version's independently hand-written legend line.

**Per-series y-axis scaling, and decoupling "Graph fields" from "Fields" (Christer, same day, two more rounds of follow-up on the chart above).** First: "dont be so fixated of the y axis unit, let them work around (min+max)/2 at the middle of y axis" - the chart originally forced a `Math.min(0, ...)` zero baseline into the y-domain, wasting most of the plot's height on empty space for any series that doesn't naturally sit near zero (`avg_speed_kmh` wandering in the 40-60 range, say). Dropping the forced zero (domain became a single pooled `[min(all series' values), max(all series' values)]`) fixed that for the single-series case, but Christer's very next message, looking at a real 5-series screenshot, caught that it wasn't actually enough: **"That doesnt look centered to me."** He was right - a pooled/shared domain across multiple series still lets one large-magnitude series (`duration_seconds`, in the thousands) flatten every smaller-magnitude series (`distance_km`, `avg_speed_kmh`, `elevation_gain_m`) into a sliver near the bottom, centered on paper but useless to actually read. `stats.html`'s chart script now scales every series to its *own* independent `[min, max]` domain (`yFor(value, s)` takes the series, not just the value) - so each series' own `(min+max)/2` lands at the vertical center and each uses the chart's full height, regardless of what unit or magnitude any other graphed series happens to have. The tradeoff: one shared numeric y-axis no longer means anything once more than one series is on screen, so gridline value labels are only drawn for the single-series case (mathematically identical to the old pooled behavior when there's just one field); with multiple series the gridlines stay as plain unlabeled reference lines and each series' own observed min-max range is printed in its legend entry instead (hover still shows exact per-point values either way). Bar-mode's baseline simplified to a single constant (`padTop + plotH`, the bottom of the plot) since every series' own domain minimum maps there by construction now.

Same message, second half: **"Why 15 fields but only 5 graph fields."** The "Graph fields" checkbox list used to only ever show whichever of the 15 `STAT_FIELDS` also happened to be checked under "Fields" above it (the report table's own column selection, defaulting to 5 via `DEFAULT_FIELDS`) - an artificial coupling between two independent questions ("what should the table show" vs. "what should the chart plot"). `_selected_graph_fields()` no longer takes a `selected_fields` argument at all, and the template's checkbox loop lost its `{% if key in selected_fields %}` gate, so all 15 fields are always offered as graph options. Since a field can now be graphed without being a report column, `stats_dashboard()` gained `_fields_for_aggregation(selected_fields, graph_fields)` - the ordered, deduplicated union of both lists - and both of its `aggregate_recording_stats()` calls (the main buckets and the `grouping="all"` summary) now aggregate that union instead of just `selected_fields`, so a graph-only field actually has data in `bucket.values` rather than silently rendering an empty series.

`--estimate-gaps` (see `docs/man/bv-stats.md`'s "Estimating missing distance" section) is a checkbox on the form; when a bucket actually needed to fill a gap, both the summary and per-bucket table rows show the estimated portion as a separate, clearly-labeled figure next to the real total - never silently blended in - the same visibility `bv-stats`' own text/JSON output gives it.

Boundary bridging (see `docs/man/bv-stats.md`'s "Bridging cross-recording gaps" section - Christer: "based of time can you see how much of the distance belong to each recording id") needs no checkbox at all, since it's a real GPS-derived distance rather than an extrapolation: `aggregate_recording_stats()` computes it unconditionally whenever `distance_km` is among the aggregated fields. When it contributes to a bucket, `stats.html` shows it the same way `--estimate-gaps` shows its own figure - a separate, clearly-labeled amount next to the real total, driven by `StatBucket.bridged_distance_km`/`bridged_recording_count` rather than `estimated_distance_km`/`estimated_recording_count`.

**Per-recording (ungrouped) charting - Christer: "Is it possible to plot the graph a recordingid at a time for non-grouped graphs."** A new `"recording"` value in `stats_report.GROUPINGS` - one bucket per individual recording, keyed by the recording's own id rather than a calendar period. Needed zero changes in this file or in `app.py`/`stats.html`: the `--group` dropdown, the chart script, and the per-bucket table rows are all already fully generic over whatever `GROUPINGS` contains, so the one-line bucketing change in `stats_report.py` (using `str(recording_id)` as the bucket key instead of `_bucket_key()`'s calendar-derived one) was the entire implementation. Meant for a narrow selection (a single day, a single trip) so the chart plots one point per recording rather than a rolled-up total - picking it over a wide range works the same way, just with one bucket per recording in that range, by design rather than as a bug.

**Build-up animation + legend click-to-toggle (Christer, 2026-08-23): "I couldnt see the date graph building 1 date at a time. And can clicking on the legend toggle the data for it off and on?"** Disambiguated via a clarifying question first, since "couldn't see it building 1 date at a time" could equally have meant a data bug - Christer confirmed it meant an animated build-up, not broken data. Both features are entirely client-side, inside `stats.html`'s existing inline `<script>` - no `chart_data_json`/route/`stats_report.py` changes needed, since both just control how the already-computed `series` payload gets drawn and shown. Every bar `<rect>`/point `<circle>` gets `data-series="<seriesIndex>"` and `data-x-index="<i>"` attributes when built; a `reveal()`-style loop walks x-index `0..n-1` on a `window.setTimeout` stagger (`stepMs = totalAnimMs / n`, `totalAnimMs` capped to `[300, 1500]` regardless of how many buckets are in a wide selection, e.g. a year of `--group date`) clearing each step's elements' `opacity` from `0` back to unset - "unset" rather than explicitly `1`, so `base.html`'s existing `.stats-chart-bar:hover`/`.stats-chart-point:hover` dimming rules (plain CSS, lower specificity than an inline style) still take effect once an element is visible, rather than being permanently shadowed by an inline `opacity: 1`. The line chart's polyline itself additionally animates via the classic stroke-dash technique (`stroke-dasharray`/`stroke-dashoffset` set to the path's own `getTotalLength()`, transitioned to `0`) so the line visibly draws left-to-right over the same `totalAnimMs` window the points stagger-reveal across. `window.matchMedia('(prefers-reduced-motion: reduce)')` skips all of this (`totalAnimMs = 0`, everything starts fully visible) - a new accessibility consideration for this page, not used elsewhere in `bv-web`.

Legend click-to-toggle reuses the same `data-series` tagging: each `.stats-legend-item` in `#stats-legend` is now a real, keyboard-operable toggle (`role="button"`, `tabindex`, click/Enter/Space all wired to the same handler) rather than inert text. Clicking flips a `seriesVisible[seriesIndex]` boolean and immediately sets every matching `[data-series="<index>"]` element's opacity (bars, points, and the polyline together) to match - deliberately immediate rather than waiting on the build-up stagger, since a click is a deliberate action; any x-index the reveal loop hasn't reached yet still respects `seriesVisible` at the moment its own step fires, so a series toggled off before the animation reaches it never flashes on. `base.html` gained `.stats-legend-item-off` (fades both the swatch and label) plus `cursor: pointer`/hover styling, so the on/off state reads at a glance without a second icon.

**Follow-up, same day: "graph is still not animated, but toggle legends works great."** The blank-chart regression above was fixed, and the legend toggle (built on the same `data-series` tagging) worked fine, but the build-up reveal itself still never visibly played for Christer. Static review of the reveal loop found no logic bug, and Christer explicitly declined ("i will not write that") to run a one-line DevTools check of `prefers-reduced-motion` for me, so the fix had to be robust to an unconfirmed cause rather than targeted at a diagnosed one. The original implementation scheduled N separate `window.setTimeout` calls at page-build time, one per x-axis index (`delay = index * stepMs`) - exactly the kind of thing a backgrounded/inactive browser tab throttles or coalesces (Chrome in particular clamps and batches timers heavily once a tab loses focus), which would make every "step" fire in one indistinguishable burst the moment the tab regained focus, looking identical to "no animation happened" regardless of whether `prefers-reduced-motion` was actually the cause. Reworked to a CSS `transition-delay`-driven reveal instead: each bar `<rect>`/point `<circle>` gets its own `transition: opacity 200ms ease <index * stepMs>ms` set once at element-creation time (a `revealTransition(index)` helper, alongside the existing `opacity: 0` starting state), and the reveal trigger itself collapses to a single `void container.offsetHeight` reflow-force plus one paired `requestAnimationFrame` call that flips every tagged element's opacity in one shot - the same "force a real paint between the hidden and visible writes" pattern the line chart's own stroke-dashoffset draw-in animation already used a few lines above it. The stagger is now timed entirely by the CSS engine's own per-element `transition-delay`, not by N entries on the JS event loop, so it can't be throttled or batched the way the timer-based version could. One trap this rework introduced and then had to close: `applySeriesVisibility()` (the legend-toggle handler) sets `el.style.opacity` on the same elements, but doesn't reset `transition`, so a legend click after the initial reveal would otherwise replay that same baked-in per-x-index delay (up to 1.5s) instead of toggling immediately - fixed by having `applySeriesVisibility()` overwrite `el.style.transition` to a plain `'opacity 200ms ease'` (no delay) on every toggle, and picked up the same `opacity: '' `-when-visible /`0`-when-hidden pattern the reveal loop already used (it had been using a literal `1`/`0`), so the `:hover` dimming rule in `base.html` isn't permanently shadowed by an equal-specificity inline style either way. Verified via the same hand-rolled fake-DOM harness used for the earlier regression - extended to support bare attribute-presence selectors (`[data-x-index]`, used by the new single-pass reveal trigger) alongside its existing `[attr="value"]` support - confirming zero `window.setTimeout` calls are scheduled at all now (the whole reveal is synchronous CSS-property writes) and that both bar and line chart types build/reveal without a thrown exception, plus a repeat Jinja2-render check.

**Same day, second follow-up: the CSS-transition rework above still wasn't enough on Christer's real archive.** He sent a screenshot of an actual "by date" chart over his full archive (2026-01-02 through 2026-08-23, ~220 distinct dates, 5 series) with the comment "This didn't exist until it came without animation" - the chart simply popped into existence, no visible build. The remaining bug: `stepMs` was still `totalAnimMs / n` with `totalAnimMs` capped at 1500ms regardless of `n` - fine for a handful of x-positions, but at `n≈220` that's roughly a 7ms delay between neighboring x-indices, an order of magnitude below anything perceivable as a left-to-right stagger; every point's fade-in overlaps almost completely with its neighbors', reading as instantaneous. This was never actually about `prefers-reduced-motion` or timer throttling - both real, defensible hypotheses given what was known at the time, but the actual cause only became visible once a wide real-world date range was tested, something the earlier small synthetic test fixtures never exercised. Fixed by capping the *number of animation steps* (`maxAnimSteps = Math.floor(MAX_TOTAL_MS / MIN_STEP_MS)`, currently 50 steps at a 40ms floor within a 2000ms ceiling) rather than only the total duration: `revealTransition(index)` now buckets each x-index into one of `animSteps` groups (`Math.floor(index / n * animSteps)`) instead of giving every index its own delay slot, so neighboring x-indices in a wide chart share a reveal step rather than each getting an imperceptibly-close one of its own - for `n` at or below the step cap, bucketing is a no-op (each index gets its own bucket, identical to before). Verified with the harness fed a synthetic 220-key dataset matching Christer's real range: confirms 50 distinct delay values 40ms apart spanning 0-1960ms (previously would have been ~220 delays under 10ms apart), and that a small `n=4` case still produces one delay per index (75ms apart, 225ms total) - unchanged small-selection behavior. Re-ran `node --check`, the full harness suite (bar + line, zero scheduled timers), and the Jinja2-render check.

**Same day, third follow-up: "Stil no animation, i cant scroll down until the graph is fully drawn."** A different symptom from the first two - the whole page was unresponsive, not just the chart failing to visibly stagger. Root cause: `svg` is attached to the live document from the very start (needed for `getTotalLength()`, see the "No graph visible" regression above), and every bar/point was being appended to it individually - one `svg.appendChild(rect)`/`svg.appendChild(circle)` call per element, hundreds of times over for a wide date range (Christer's real chart: ~220 dates x up to 5 series = up to 1100 elements). Each append to an already-attached, already-rendering SVG risks a synchronous style/layout recalculation in the browser; hundreds of those back-to-back is real main-thread work that blocks input - including scrolling - for however long the whole build takes, and by the time the script finally returns control to the browser the chart is already fully built, so there's nothing left to visibly animate even though the CSS transition-delay machinery from the two fixes above is working correctly. Fixed by batching each series' elements into a detached `DocumentFragment` (`pointsFragment` for line-chart circles, `barsFragment` for bar-chart rects) during the build loop, and appending that whole fragment to `svg` once per series instead of appending each element as it's created - appending to a fragment has no live-document cost at all, so the hundreds of individual mutations collapse into one bulk insert per series. The one already-live element per series, the polyline itself (still needed attached for `getTotalLength()`), is unaffected and keeps its own direct `svg.appendChild(path)`. Verified by instrumenting the fake-DOM harness's `appendChild` to count only appends whose *target* isn't itself a fragment (i.e. real live-DOM mutations): a synthetic 220-date, 2-series line-chart run dropped from what would have been ~442 individual live appends (440 circles + 2 polylines) down to 27 (2 polylines, 2 fragment-bulk-inserts, plus the fixed-count gridlines/axis-labels/tooltip/legend overhead already present) - confirming the fragment batching actually removes the per-element live-DOM cost rather than just moving it around. Also extended the fake-DOM harness with `document.createDocumentFragment()` and fragment-aware `appendChild` (merges a fragment's children into the target rather than nesting the fragment itself, matching real DOM semantics) to make this instrumentation possible. Re-ran the full suite: `node --check`, harness runs for both chart types (still zero scheduled `setTimeout` calls, no thrown exceptions), and the Jinja2-render check confirming `createDocumentFragment`/`pointsFragment`/`barsFragment` all appear in the rendered output.

**Same day, fourth follow-up: "There is no area to scroll down to see the animation, before the complete graph is created. Sp no it dont woek."** Clarified that the previous "can't scroll" report wasn't really about scrolling at all - the chart fits on screen without scrolling, and it still just appeared already fully drawn, exactly as every prior report described. That's the tell: three separate, independently-verified fixes (reveal mechanism, timing, main-thread blocking) each addressed a real potential cause, yet the failure mode never varied even slightly - not "too fast," not "half-animated," just unconditionally absent, every single time. **Regression, same day: "No graph visible."** The line chart's draw-in animation calls `polyline.getTotalLength()` (see above) immediately after building the polyline - but the surrounding `<svg>` itself was only attached to `#stats-chart` at the very end of the script, after every bar/point/line had already been built into it. Query params, `_selected_stat_fields()`/`_selected_graph_fields()`/`_fields_for_aggregation()`, and every downstream behavior are unchanged; this was a template-only layout change. `base.html` gained `.stats-fields-table`/`.stats-fields-checkbox-col` (tighter padding than the plain report-table styling, since 15 dense rows of "name + two checkboxes" reads better compact than at the report table's own roomier spacing).

## Job runner

`bv-config`'s wizard needs to ask questions back, and any of the wired-in commands can run for a while (`bv-export`'s own rendering especially, `bv-download` on a large range) - neither fits the request/response shape of an ordinary route. `web/jobs.py` (`JobRunner`, `Job`, `JobStatus`) runs each triggered command in a background `threading.Thread`, **in-process, not a subprocess**: the job runner calls the target CLI module's own already-tested `_run()` function directly (`cli/bv_config.py`, `cli/bv_gps.py`, `cli/bv_download.py`, `cli/bv_generate.py`, `cli/bv_export.py`, `cli/bv_ls.py`, `cli/bv_scribe.py`, `cli/bv_search.py`), passing it `ask`/`say`/`warn` callables that write into that job's own `Job.output` list instead of a real terminal.

This sidesteps a real problem a subprocess approach would have: a subprocess's stdout can't reliably tell "waiting for input" apart from "more output is still coming", since `input()`'s own prompt text has no trailing newline - scraping raw bytes for that would need fragile heuristics. Calling the real Python function directly means the job runner controls exactly when `ask()`/`say()` fire, no scraping needed. It also means each job's `ask`/`say` closures only ever touch that one job's own output list, not the real process-wide `sys.stdout` - safe for jobs to run concurrently without a global-redirect hazard.

`bv-config`'s `prompt()`/`edit_endpoints()`/`run_wizard()`/`_run()`, `bv-gps`'s `_run()`, `bv-generate`'s `_run()` (and every internal helper it calls - not just the top-level function, since `bv-generate`'s own tests call several of those helpers directly without passing `say`/`warn`, so they all needed real-`print` defaults too), `bv-export`'s `_run()`, and `bv-download`'s `_run()`/`_capture_record_time()` all gained injectable `ask`/`say`/`warn` keyword-only parameters for this, defaulting to the real `input`/`print`/stderr-`print` - real terminal use is unaffected. `bv-ls`'s own `print_trips()`/`bv_ls()`/`_run()` got the same treatment, but with only `say` - it has no warnings or prompts of its own, so there's no `ask`/`warn` to thread through. `bv-scribe`'s and `bv-search`'s own `_run()`s already had injectable `say`/`warn` keyword-only parameters from when they were originally built (see their own `WORKING_CONTEXT.md` entries), so wiring them into the job runner needed no CLI-side refactor at all - `start_bv_scribe()`/`start_bv_search()` below could be added directly. That refactor also had to fix a real formatting hazard: `bv-ls`'s grouped (non-`--trips`) table used to build each header/data row across several `print(..., end=...)` calls rather than one call per line, which doesn't survive a `say` that appends one complete `Job.output` entry per call - each row is now assembled as a plain string first and handed to `say` once, byte-for-byte the same printed result, just built differently. When `ask()` is called, the job's status flips to `waiting_for_input`, the prompt text is recorded on the `Job`, and the call blocks on a `queue.Queue` until the browser POSTs an answer (`Job.submit_answer()`); the job page (`templates/job_detail.html`) shows a form for that prompt and, while running, polls `GET /jobs/{job_id}/poll` via JS `fetch()` every 2s and patches `#job-output` in place (see "AJAX job-output polling" below for why - this replaced an earlier full-page `<meta http-equiv="refresh">` reload). Polling only starts while `status == "running"` - it's suppressed once a job reaches `waiting_for_input` (and once it's finished), since patching the output out from under the owner mid-answer would be as disruptive as a reload wiping the field; the page instead only reloads again once the owner's own `POST /jobs/{job_id}/answer` redirects back. It's also suppressed by a `?paused=1` query param the job page's own "Pause auto-refresh" link sets - added after Christer hit a real problem reading a long job's output on the old meta-refresh version: every 2-second full-page reload snapped scroll back to the top, so reading anything above the very bottom of a still-running job's transcript kept getting yanked out from under him. Pausing freezes the page on its current snapshot (a plain link toggle, not JS, the same server-rendered pattern the archive browser's own filters use); a "Resume auto-refresh" link drops the param again. Jobs are held in an in-memory `dict` on `JobRunner` - the same restart-loses-state trade-off `SessionStore` already accepts (a job mid-run doesn't survive a restart regardless of whether it's tracked).

**Persistent output log (`core/joblog.py`)**: Christer, after restarting `bv-web` to clear stuck GPU memory and losing all record of what had been running: "I would also want a logfile of all the output." `Job.append_output()` mirrors every line into a single append-only, gzip-rotated-monthly transcript (`~/beyond-video-data/logs/beyond-video-YYYY-MM.log`, one file per calendar month, oldest gzipped copies pruned after 12 months) alongside the in-memory `Job.output` list it always wrote to - tagged with the job's own prog name (the first word of `Job.command`, e.g. `bv-scribe`, reused rather than threading a dedicated field through all eight `start_bv_*()` methods just for this). Direct-CLI runs get the identical coverage on the other side: each `cli/bv_*.py`'s own `main()` wraps its `say`/`warn` callables through `wrap_say()`/`wrap_warn()` before calling `_run()`, so the same rotating logfile covers a command typed straight into a terminal and one triggered from the browser - "direct CLI calls too, not just bv-web jobs" was the settled scope. Rotation is monthly and in-process (a custom `MonthlyRotatingFileHandler`, not `logging.handlers.TimedRotatingFileHandler`, which has no monthly `when` unit since months aren't a fixed number of seconds) rather than external cron/logrotate - the dual NAS-Docker/PC-native deployment means there's no single place an external scheduler could reliably reach both. `default_logs_dir()` (`core/camera_config.py`) resolves the directory the same override-then-fallback shape `default_config_dir()` uses - `BEYOND_VIDEO_LOGS_DIR` if set, otherwise `~/beyond-video-data/logs` - and both Docker services set that variable to a shared mounted folder (see `docker-compose.yml`), since without it a `bv-cli` container's own transcript would vanish the moment its `--rm` run exits. The companion command-history feature (`core/history.py`, a structured index of command+timestamp+duration+status+options, distinct from this raw output transcript) writes `history.jsonl` alongside these logfiles - see the next paragraph for the command/page that reads it back.

**Persistent command history (`core/history.py`, `blackvue/history.py`, `bv-history`)**: the structured half of the same ask - one JSON-Lines entry per `bv-*` invocation (`command`, full `command_line`, `source` `cli`/`bv-web`, `username` for bv-web jobs, `started_at`, `duration_seconds`, `status`), appended to `history.jsonl` in the same `default_logs_dir()` the output logfiles above live in. Two write sites, mirroring the output-log's own two call sites: `cli/errors.py`'s `run_cli()` - the one wrapper every `bv-*` CLI's `main()` already calls - records one entry per invocation in a `finally` block (fires exactly once regardless of success/failure/`KeyboardInterrupt`/an unhandled exception), and `web/jobs.py`'s `JobRunner._spawn()` records one entry per job once its background thread reaches a terminal status. `blackvue/history.py` is the read-side library both `bv-history` and bv-web's own `/history` page share: `all_entries()`/`filtered_entries()` number every entry by absolute oldest-first position (the same convention bash/pwsh's own `history` uses - a filtered view still shows each match's real original number, not a 1..N renumbering), `tail()` limits to the most recent N, and `matching_log_lines()` best-effort reconstructs one entry's full output from `core/joblog.py`'s own timestamped lines - matching by prog-name tag within the entry's own `[started, started+duration]` window (converted from `started_at`'s UTC to the output log's naive-local-time timestamps first). `GET /history` (owner-only, same gating as every other job/admin route) renders a filterable table (`--command`/`--camera`/`--search`/`--from`/`--until`/`--timestamp`/`--failed-only`/`--source`, all reusing `HistoryFilter`/`filtered_entries()` directly rather than a separate web-side query layer) with the same tail-by-default-15/`--all`-for-everything behavior the CLI has; `GET /history/{number}` shows one entry's full logged output, the web equivalent of `bv-history show <id>`.

**Reuse a previous run's parameters (`HistoryEntry.params`, `Job.params`, `_recent_web_runs()`/`_reuse_defaults()` in `app.py`) - bv-scribe pilot.** Christer: "i would like to have a button or something like in bv-web to get the latest run parameters filled in for bv-web or maybe a list of the latest" - answered "Both" when asked to choose between prefill-only, pick-from-a-list-only, or combining the two. Rather than reconstructing an `argparse.Namespace` by re-parsing `Job.replicate_command`/`HistoryEntry.command_line` (fragile - would need `shlex`-splitting plus a per-command `parse_args()` call plus inverting every negative flag back to its web-form shape), the raw web-form field dict is captured directly in `app.py`'s own `POST /jobs/bv-scribe` route, before `_clean()`/type-conversion/flag-inversion touches it - keyed identically to the `GET` form's own `name=` attributes (confirmed FastAPI's `Form(...)` parameters use the Python parameter name as the HTML field name, no alias, by grepping the template's own `name="from_"` etc. against the route's matching kwarg). That dict threads through `start_bv_scribe(params=...)` -> `Job.params` -> `HistoryEntry.params` (persisted to `history.jsonl` alongside every other field) -> read back by the `GET` route. `HistoryEntry.params` is `dict | None`, not defaulting to `{}`, so "no params recorded" (a CLI entry, or a bv-web entry from before this feature existed) stays distinguishable from "recorded an empty dict" - both `core/history.py`'s `record()`/`read_entries()` needed no changes at all, since `asdict()`/`json.dumps()` and `HistoryEntry(**data)` already handle a new optional field transparently. `_recent_web_runs(command)` (`app.py`) filters `filtered_entries(HistoryFilter(command=..., source="bv-web"))` down to entries that actually have a `params` snapshot, newest first; `_reuse_defaults(recent_runs, reuse_param)` resolves the form's `defaults` dict plus which entry (if any) is "active" - `?reuse=<N>` if it names a real entry, otherwise the most recent one, otherwise `({}, None)` when there's no history yet, falling back to the form's own ordinary hardcoded defaults unchanged. `?reuse=<N>` mirrors the existing `?tail=1`/`?paused=1` toggle-link convention (see below) - a plain server-built URL, not JS. `job_new_bv_scribe.html` binds every field's `value`/`checked`/`selected` to `defaults.get(...)` (falling back to its own prior hardcoded default, e.g. `task` still defaults to `both` with no history at all) and shows a "Reuse a previous run" panel above the form listing recent runs as links, the active one highlighted - originally capped at the 5 most recent, uncapped after Christer: "i dont want to be restricted to 5" (each route now passes `_recent_web_runs()`'s full list; `.reuse-list` in `base.html` grew a `max-height`/`overflow-y: auto` so a long history scrolls within the panel instead of growing the page). Implemented as a pilot on `bv-scribe` alone first (verified end-to-end, tests + template-render checks passing), then extended to `bv-export`/`bv-generate`/`bv-search` - the identical pattern, no changes to the mechanism itself: each command's `start_bv_*()` gained the same `params: dict | None = None` kwarg threaded straight into `_new_job(..., params=params)`, each `GET`/`POST` route pair gained the same `recent_runs`/`defaults`/`active_reuse_number` computation and raw-form-dict capture, and each template gained the same reuse panel plus `defaults.get(...)` on every field. `bv-gps`/`bv-download`/`bv-ls` were deliberately left out of this rollout (see `_REUSE_SUPPORTED_COMMANDS` in `app.py`) - their own forms are small enough, or their own flags change little enough run to run, that a "reuse a previous run" picker adds more UI than it saves; `bv-config` stays excluded for the same interactive-wizard reason as before.

**Two UI mechanisms, not one.** Christer, choosing between an in-page picklist and a link from `bv-history`'s own pages: "I love you. Lets work backwards. I agree on which commands should have this feature. I like both both options a collapsed list and the bv-history link. So i think to myself why choose, when i can have both." Both ship together: (1) the in-page "Reuse a previous run" panel described above, now a collapsible `<details>`/`<summary>` (`.reuse-panel` in `base.html`, sharing `.option-group > summary`'s exact disclosure-triangle styling) rather than bv-scribe's original always-visible `<div>` - "I think this panel should be an expandle list at the top, just to not steal to much space from the page" - open by default only when a specific `?reuse=<N>` is active, collapsed otherwise; and (2) a "Rerun"/"Rerun with these options" link on `/history` (`history_list.html`, a column on each row) and `/history/{number}` (`history_detail.html`, under the details table), pointing at `/jobs/{entry.command}?reuse={number}` - the exact same URL shape the in-page panel's own links already use, so both mechanisms resolve through the identical `_reuse_defaults()` code path. A history row only gets a Rerun link when `entry.source == "bv-web"` (a CLI invocation has no web form to have snapshotted `params` from), `entry.params` is truthy, and `entry.command` (the bare prog name `core/history.py`'s own `record()` derives via `job.command.split(maxsplit=1)[0]` - confirmed by reading `_record_job_history()`'s own docstring, not "bv-export kirby" as `Job.command` itself reads) is in `_REUSE_SUPPORTED_COMMANDS` - the same four-command set the in-page panels themselves cover, defined once in `app.py` and passed into both history templates' context so the gating logic lives in exactly one place.

**`bv-download`'s own wrinkle: a real interactive prompt that must never actually run here.** Unlike `bv-config` (built around `ask()` throughout its wizard), `bv-download` has exactly one interactive moment - `confirm()`'s plain `input()` call, gated behind `sys.stdin.isatty() and sys.stdout.isatty()` - and it was never converted to go through `ask()`, because there was no need to: `start_bv_download()` always appends `--yes` to the argv it builds, regardless of what the web form said, so `confirm()` is never reached from a job. This isn't just belt-and-suspenders around the tty check (which would likely already be `False` inside a backgrounded web-server process) - it's the only safe option, since `confirm()`'s `input()` reads the real process stdin, which this job runner has no way to answer through its own `ask()`/`Job.submit_answer()` mechanism. A stray real-stdin block here would hang the job forever with no way for the browser to unblock it, unlike `bv-config`'s wizard, which is built around exactly that kind of exchange. `--host`/`--target`/`--config-dir` are also not exposed on the web form, for the same "curated, not an arbitrary-connection escape hatch" reasoning `bv-gps`'s own omitted `--host` already established - `start_bv_download()` only ever takes an already-configured camera id. One more small deliberate gap: `--trace`'s progress dots print straight to real stdout, not through `say()` - a partial-line, no-trailing-newline stream has no sensible representation in `Job.output`'s list-of-complete-lines shape, so a `--trace` job's dots land in `bv-web`'s own process console/log instead of the job's browser-visible output, same as any other `--trace` run whose stdout isn't a live terminal.

`bv-gps`'s job trigger only accepts an already-configured camera id, not its CLI's own `--host` option - `--host` is a terminal-only "probe a bare IP that hasn't been set up with bv-config yet" escape hatch, not something the browser-facing job form should expose. `bv-generate`/`bv-export`'s job triggers resolve their camera's archive path the same way the archive browser does (`app.py`'s `_find_camera_archive()`), rather than taking a raw path from the form. `bv-scribe`/`bv-search` follow the exact same `_find_camera_archive()` resolution - "you can use the camera id just like the others" was Christer's own framing for wiring them in. `bv-download` is different again: its own positional CLI argument already *is* the camera id (not a bare archive path), so `start_bv_download()` doesn't call `_find_camera_archive()` at all - it just passes the id straight through in the argv it builds, the same shape `start_bv_gps()` already uses, and lets `bv_download._run()` do its own config lookup exactly as a real terminal invocation would.

**bv-export's `_run()` and its own real `SystemExit`**: unlike the other three commands, `bv_export()` (the function `bv-export`'s CLI has always called) legitimately raises `SystemExit` itself in two places (an empty `--duration-heal-archive` request, a bad `LexicalTimeParser` value) - a tested public contract (`test_bv_export.py` asserts `pytest.raises(SystemExit)` around a real call), so it couldn't just be converted to a `warn()` + return like an ordinary error. The new `bv_export._run()` wrapper (used by both `main()` and the job runner, mirroring every other bv-* command's own `_run()` shape) catches that `SystemExit` at exactly that one call site and turns it into `warn(str(exc)) + return 1` instead - `bv_export()` itself keeps raising exactly as it always did, so its existing test contract is untouched. `JobRunner._spawn()`'s own completion handler additionally catches `SystemExit` alongside the usual `Exception` as defense in depth (`SystemExit` subclasses `BaseException`, not `Exception`, so a bare `except Exception` would silently miss one and leave a job stuck showing `running` forever) - not a substitute for handling it at the source, since none of this project's own `_run()`s should ever actually let one escape that far.

**bv-export's `parse_args()` extraction**: `bv-export`'s argument parser used to be built inline inside `main()`, with no reusable way to turn a web form's own argv into parsed `args` the way `bv-config`/`bv-gps`/`bv-generate` already could via their own standalone `parse_args()` functions. Pulled out into its own `bv_export.parse_args(argv)` - the identical `parse_args()`/`main()` split every other bv-* CLI already uses - purely mechanical (`main()` now just calls it), confirmed by the existing 109-test suite passing unchanged.

**Cancellation** (`Job.cancel()`/`JobRunner.cancel()`, a "Cancel job" button on `job_detail.html` whenever a job isn't finished) is honest about what Python can and can't do to a running thread. A job currently `waiting_for_input` is unblocked immediately: `cancel()` pushes a sentinel onto the job's own answer queue, `ask()` recognizes it and raises `_JobCancelled`, which unwinds `_run()` right away - the same as any other exception escaping it. A job that's `running` with no prompt open (e.g. `bv-gps` blocked inside a socket call) can't be interrupted mid-call - `cancel()` instead flips the job's status to `CANCELLED` immediately so the browser stops trusting its output, while the background thread itself may keep running invisibly (it's a daemon thread, so it can't block process shutdown either way) until whatever it's blocked on returns or times out on its own; `JobRunner._spawn()`'s completion handler checks for this and won't overwrite an already-`CANCELLED` status with a stale success/failure result if the thread does eventually finish.

Most job routes (`GET`/`POST /jobs/bv-config`, `GET`/`POST /jobs/bv-gps`, `GET`/`POST /jobs/bv-download`, `GET`/`POST /jobs/bv-generate`, `GET`/`POST /jobs/bv-lock`, `GET`/`POST /jobs/bv-export`, `GET`/`POST /jobs/bv-ls`, `GET`/`POST /jobs/bv-scribe`, `POST /jobs/{job_id}/answer`, `POST /jobs/{job_id}/cancel`) are gated by `require_owner` rather than a granular per-command permission system - simpler, and there's currently no real semi-trusted third party that would need finer-grained access for most of these.

**bv-search is the one carve-out** (`GET`/`POST /jobs/bv-search`, and `GET /jobs/{job_id}` for a bv-search job specifically): gated by `require_viewer_or_owner` (`web/auth.py`) instead, so any logged-in viewer can run a search and see its results, not just the owner - see WORKING_CONTEXT.md's "let bv-web viewers run bv-search" note for why bv-search specifically (read-only over already-generated text/GPS, doesn't create/modify/consume GPU-CPU the way every other job type does). `GET /jobs/{job_id}` is shared by every job type though, so it can't just swap its dependency wholesale - it stays open to any logged-in user, but checks `job.command.startswith("bv-search ")` itself and 403s a non-owner viewer trying to load any other job type's detail page (e.g. by guessing/reusing a job id). The Search nav tab in `base.html` moved out of the owner-only block accordingly; every other job-trigger tab (and the History tab) stayed inside it.

**`Job.replicate_command`**: every `start_bv_*()` method also builds the equivalent real `bv-*` CLI invocation and stores it on the `Job`, shown on `job_detail.html` with a "Copy" button (Christer: "Is it possible for every bv-* command to print out how its called in bv-web, so i can replicate it in pwsh or bash later?"). Built from the exact `argv` each method already assembles for its own `parse_args()` call, with one deliberate substitution: the archive-scoped commands (`bv-ls`/`bv-generate`/`bv-lock`/`bv-export`/`bv-scribe`/`bv-search`) swap the resolved server-side `archive_path` (e.g. `/data/archive/Kirby`, meaningless outside this container) back out for the plain `camera_id` they were given alongside it - the same id a terminal invocation would use directly, resolved fresh wherever it's pasted as long as that machine also has the camera configured via `bv-config` (Christer's actual dual-machine NAS+PC setup already relies on exactly this). `bv-config`/`bv-gps`/`bv-download` need no substitution, since their own positional argument already *is* the camera id, not a resolved path. `_quote_for_replicate()` wraps a value in double quotes only when it contains whitespace or is empty (e.g. a `--place "Slussen, Stockholm"`) - deliberately not `shlex.quote()`'s single-quote style, which is bash-only and would confuse someone pasting the same line into PowerShell; this is a "good enough for realistic values" convenience, not a fully correct dual-shell quoting implementation (an embedded double quote is escaped with a backslash, which isn't strictly correct PowerShell syntax, but none of this project's own argument values ever contain one). The string also includes whatever flags a job-trigger method always forces on itself (e.g. `bv-download`'s own `--yes`) - it shows what actually ran, not a hypothetical bare terminal command.

**`?tail=1` (quick tail view, task #687).** A long-running job's output grows every 2-second auto-refresh tick, re-sending and re-rendering the whole history each time - a real problem on an 800+-recording `bv-scribe` batch. `job_detail()` accepts `?tail=1` on a still-running job (ignored once a job finishes - a finished job's full output isn't growing anymore, so there's nothing to save by tailing it) and renders only the last `TAIL_LINE_COUNT` (30 - originally 200, lowered after Christer measured his own job-output panel only actually shows ~24 lines before scrolling, so the extra buffered lines were pure re-render/re-send cost with no visible benefit) lines instead of the full list, with a "N earlier line(s) hidden - show full output" note and a toggle link. `paused` and `tail` are independent query params that can combine (`?paused=1&tail=1`) - `job_detail()` builds each toggle link's `href` server-side (`tail_on_url`/`tail_off_url`/`pause_url`/`resume_url`) rather than string-concatenating in the template, so flipping one param never silently drops the other.

**`pre.job-output` scroll-to-bottom.** The server-side `?tail=1` slicing (above) was always correct - it always sliced the real last `TAIL_LINE_COUNT` lines - but Christer still saw what looked like stale progress: "still showing the first 30 rows... it started on 50 instead of 203." Root cause: `pre.job-output` (`base.html`) is a fixed-height scrollable box (`max-height: 60vh`) that only shows ~24 lines before it needs scrolling, and a bare `<pre>` always starts scrolled to its own top - so even a correctly-sliced 30-line tail rendered with only its *oldest* ~24 lines visible above the fold, looking like stale output. `job_detail.html` gained an `id="job-output"` on the `<pre>` plus a small inline `<script>` that sets `scrollTop = scrollHeight` on the page's initial load. (Original fix relied on every subsequent update also being a full reload via `<meta refresh>`, so the same script re-ran automatically each tick; superseded by the AJAX poll loop below, which instead re-checks proximity to the bottom before each in-place patch - see "AJAX job-output polling".)

**`GET /jobs/{job_id}` sends `Cache-Control: no-store`.** Christer hit a real bug: starting a job, navigating away (e.g. to trigger `bv-ls`), then hitting the browser's Back button showed stale output until he manually reloaded. That's the browser's back/forward cache (bfcache) restoring the exact DOM snapshot from when he left rather than making a new request - a page's own periodic refresh (whether the old `<meta refresh>` or the current AJAX poll loop) never gets a chance to fire again since no new page load happens on Back. `no-store` tells the browser this response can never be served from cache, forcing Back (and any other cached-navigation path) to always re-fetch, so it now shows current status/output the same as a manual reload would. `GET /jobs/{job_id}/poll` sets the identical header for the identical reason (see below).

**AJAX job-output polling (task #772-776) - replaced the `<meta http-equiv="refresh">` full-page reload.** Christer's report: resizing or restoring the browser window while a GPU-heavy `bv-generate` job (NVENC encode and/or CUDA Whisper/scene-description inference) was running would sometimes turn the screen to "an old TV going crazy" with a "sssssss" audio glitch, several times over - a Windows GPU driver TDR (Timeout Detection and Recovery) reset from GPU contention between the running job and the browser's own GPU-accelerated compositor, not a `bv-web` bug as such. The old `<meta http-equiv="refresh" content="2">` made this measurably worse: a full page reload rebuilds *everything* - layout, the full-page background image, the entire output block - every 2 seconds regardless of whether anything actually changed, and lining one of those reloads up with a resize/restore was enough to tip an already GPU-starved driver over. It also had its own independent, non-GPU annoyance: always snapping scroll back to the top, fighting anyone reading further up in a long job's output (see `?paused=1` above, which existed specifically to work around that). The fix: `job_detail.html`'s output block was extracted into a shared partial (`templates/_job_output_lines.html`, expecting the same `output`/`camera_id` context `job_detail()` always built, plus the `is_recording_id` Jinja global) so it renders byte-identically whether reached via the full page or the new endpoint; `GET /jobs/{job_id}/poll` (`app.py`) returns `{"status": ..., "output_html": ..., "tail_truncated_count": ...}` as JSON, sharing `_authorize_job_view()`/`_sliced_job_output()`/`_job_camera_id()` with `job_detail()` itself so a poll tick can never disagree with how the page first rendered (same permission rule, same `?tail=1` slicing). `job_detail.html`'s own inline `<script>` now `fetch()`es that endpoint every 2s while `status == "running" and not paused`, checks whether the box was already scrolled near its own bottom before patching (`box.innerHTML = data.output_html`), and only then re-pins scroll - preserving a mid-read scroll position instead of fighting it. Any status other than `"running"` (the job finished, or moved to `waiting_for_input`) triggers one real `window.location.reload()` rather than duplicating `job_detail.html`'s full conditional page furniture in JS - same for a `fetch()` failure (network hiccup or server restart), which also falls back to a reload rather than polling a dead endpoint forever. A `<noscript><meta http-equiv="refresh" content="15"></noscript>` stays as a slow no-JS fallback. This is `bv-web`'s one deliberate, scoped exception to staying JS-free elsewhere - the plain-link-toggle pattern (`?paused=1`, `?tail=1`) was preferred everywhere else specifically because it doesn't need JS, but a truly partial DOM update has no server-rendered-link equivalent. Doesn't eliminate the underlying GPU contention `bv-generate`/`bv-scribe` themselves cause (that's inherent to running NVENC/CUDA workloads on the same GPU a compositor is using) - only removes the *page's own* unnecessary full-reload churn that was making an existing hazard worse.

**Curated subset vs. full parity**: `bv-config`/`bv-gps`/`bv-download` deliberately expose only a curated subset of their own CLI flags (no `--config-dir`, no `--host`/`--target` - see above), each a specific "don't let the web form reach for an arbitrary filesystem/network target" call. Asked how much of `bv-generate`'s and `bv-export`'s own much larger flag surface the web form should expose, Christer's answer was the opposite default: "full parity but grouped by required, default and the rest" - every flag gets its own form field, organized into the same `Required`/`Defaults`/`Optional` groups described below. `start_bv_generate()`/`start_bv_export()` both build a real argv list from their own keyword parameters and run it through the target module's own `parse_args()`, so argparse's own validation (numeric ranges, mutually-exclusive groups, `--stitch-resolution`'s `WIDTHxHEIGHT` shape, and so on) is the single source of truth for what's valid - not re-implemented as a second copy of the same rules in `app.py`. The one deliberate exception, kept from the curated-subset precedent: `bv-export --target` is never a form field at all - `start_bv_export()` always uses `app.state.target`, the exact directory the Trips tab already scans, so a web-triggered export shows up there immediately and the web form can never be pointed at an arbitrary path on the server's filesystem. `bv-download` sits between the two extremes: full parity for its actual download-tuning flags (`--mode`, `--from`/`--until`/`--timestamp`, `--dry-run`, `--files`, `--verbose`, `--trace`), same argv-then-`parse_args()` pattern, but `--host`/`--target`/`--config-dir`/`--yes` are never form fields at all - the first three for the curated-id-only reasoning above, `--yes` because it's always forced on internally instead (see "Job runner" above for why forcing it, not exposing it, is the only safe option). `--files` requires `--dry-run` is `bv-download`'s only cross-field rule, so it gets the same plain `app.py` pre-check `bv-generate`'s own few conditions use, rather than a `BvExportArgError`-style exception built for a much larger validator surface. `bv-ls` lands closest to `bv-generate`/`bv-export`'s full-parity end: every flag its own CLI has gets a form field, since there's nothing destructive or slow about it and no arbitrary-target escape hatch to guard against (unlike `--host`/`--target`/`--config-dir` elsewhere). Its two numeric fields (`--max-gap`/`--gap-tolerance`) are genuinely optional - a blank field means "use `bv-ls`'s own default", not zero - so `app.py`'s route converts a non-blank value with a plain `int(...)` and re-renders the form with a friendly message on `ValueError`, rather than reaching for `BvExportArgError`'s `parse_args()`-`SystemExit`-catching machinery, which would be more indirection than two unconstrained integers need.

`bv-scribe`/`bv-search` both get full parity, like `bv-generate`/`bv-export`/`bv-ls` - but `bv-scribe`'s form uses **progressive disclosure** (the same `<details>`/`<summary>` pattern "Progressive disclosure for the bv-export web form" below established) rather than laying all ~40 flags out flat. First asked, Christer's answer sounded like "curated subset" (leave the zoom-detection/sampling knobs off the form entirely, CLI-only) - that version shipped, then got corrected: "i must have misunderstood Curated subset, i wanted it hidden like in bv-export." The actual ask was progressive disclosure, not omission: every flag still gets a real `JobRunner.start_bv_scribe()` keyword and a real form field, just collapsed by default rather than left off the form. `job_new_bv_scribe.html`'s core (camera id, time range, `--task`/`--camera`/`--model`, the plain on/off flags) stays always-visible; the sampling/model-tuning knobs (`--fps`/`--max-frames`/`--max-pixels`/`--resized-width`/`--resized-height`/`--crop-top`/`--crop-bottom`/`--max-new-tokens`/`--repetition-penalty`/`--no-repeat-ngram-size`/`--do-sample`/`--temperature`/`--top-p`/`--top-k`) live in a collapsed "Advanced sampling & model" `<details>`, the zoom-detection sub-pipeline (`--zoom-signs`/`--zoom-frames`/`--zoom-detect-width`/`--zoom-padding`/`--zoom-ocr-width`/`--zoom-max-new-tokens`/`--zoom-detect-max-new-tokens`/`--zoom-repetition-penalty`/`--zoom-no-repeat-ngram-size`/`--zoom-plate-confidence-check`) live in "Advanced zoom detection", and `--trip-summary-max-new-tokens` lives in "Advanced trip summary" - which auto-opens the moment "Also write a trip summary" is checked, the same one-directional trigger pattern `job_new_bv_export.html`'s own script already uses. `--raw`/`--config-dir` are still not exposed at all (not a disclosure question - they're an escape hatch for non-archive footage with no camera id, orthogonal to this curated-by-camera-id trigger, same as `bv-gps`'s own omitted `--host`), and neither is `--zoom-debug-dir` (a real server-filesystem path, the same "no arbitrary path as a form field" reason `bv-export`'s own `--target` was never a field either). `bv-search`, whose flag surface was always small, gets plain full parity with no disclosure needed: `job_new_bv_search.html` exposes `--text`/`--asset`/`--regex`/`--case-sensitive`, `--near`/`--place`/`--radius`, and `--trace` flat. Both still resolve their camera id to an archive path via `_find_camera_archive()`, the same as every other job trigger - "you can use the camera id just like the others" was the one constraint Christer gave up front. `start_bv_search()`'s route does one small pre-check beyond the plain argv-then-`parse_args()` pattern: at least one of text/near/place must be given (mirroring `bv_search._run()`'s own runtime check, but surfaced as a form re-render with a friendly message rather than a job that immediately fails), and a `--near` value is validated through `bv_search._parse_coordinates()` - the identical helper `bv-search`'s own CLI parser already uses for `--near`'s `type=` - via a function-scoped import, since `app.py` otherwise never imports a `cli.*` module directly at its own module scope (that's `jobs.py`'s job).

**`BvExportArgError`**: `bv-export` has dozens of `type=`/mutually-exclusive-group validators - far more than the other three commands combined - so hand-replicating each one as a separate `app.py` pre-check (the approach `bv-generate`'s own much smaller 3-condition check uses) isn't practical. Instead `start_bv_export()` runs its own `bv_export.parse_args(argv)` call under a synchronous, single-call-scoped `contextlib.redirect_stderr()` and catches the resulting `SystemExit`, re-raising the captured message as `BvExportArgError`. `app.py`'s route catches that and re-renders `job_new_bv_export.html` with the message, the same friendly-error pattern `bv-generate`'s own pre-check uses. This one narrow redirect is safe despite this module's own docstring warning against redirecting real stdout/stderr for a job: that warning is about redirecting *for the duration of a background job* while other jobs may be running concurrently in their own threads; this redirect wraps one plain, synchronous function call, entirely before any `Job` exists or any thread is spawned, so nothing else is running that could be affected by it.

**Inline snapshot preview, deleted after a second view** (`bv-gps` with `--snap` checked - the sole web entry point for a snap; the standalone `bv-snap` CLI command still exists but was deliberately never given its own web job trigger, and its earlier one was removed once `bv-gps --snap` covered the same ground and more - see "bv-snap vs. bv-gps --snap" below): a snap-capable job's `Job.snapshot_dir` is set to `default_snapshots_dir(id_)` (the same shared per-camera directory every snap run against that camera writes into); `_job_output_lines.html` renders an inline `<img>` after each "`<direction>: saved <path>`" output line (parsed via `SNAP_SAVED_RE`, served through `GET /jobs/{job_id}/snapshot/{direction}`), so the owner sees the actual pictures rather than just a text path - Christer: "Of course i want to see the snapshot pictures on bv-web." The images stay visible through the job's first finished-state page load (typically the poll loop's own automatic reload the instant the job stops running); the *next* finished-state load - a genuine manual refresh - deletes those specific files first (`_delete_job_snapshots()`, tracked via `Job.snapshot_shown_while_finished`) rather than leaving one-off snapshots to pile up on disk indefinitely - "and then deleted after page refresh." Deletion targets only the files this job's own output lines point at, never a directory wipe, since `snapshot_dir` is shared across every run against that camera.

**bv-snap vs. bv-gps `--snap`**: both CLI commands ultimately call the same `save_snapshots()` helper (`snap.py`), but `bv-gps --snap` is a strict superset - it also reports the camera's live GPS fix (coordinates, Google Maps link, address) alongside the capture. Asked "Is it overkill to have both bv-gps with snap and bv-snap inside bv-web," Christer's answer was "yes on both" (also covering the tab-order question below) - so the standalone `/jobs/bv-snap` route, its `JobRunner.start_bv_snap()`, and its nav tab were removed; `bv-gps`'s own `--snap`/`--direction` checkboxes are now the only way to trigger a snap from the browser. The `bv-snap` CLI command itself is untouched and still fully supported outside the web UI.

**Camera pick-list**: most people only ever have one camera configured, but nothing stops there being more, so the job-trigger forms don't make the owner remember/retype an id from memory. `core/camera_config.py`'s `list_camera_ids(config_dir)` scans `default_config_dir()` for `*.cfg` files and returns their ids (filenames only - deliberately doesn't parse each file, so one corrupt config can't break the listing). `app.py`'s `_camera_options()` then loads each id's config just to get a friendly `"<name> (<id>)"` label, falling back to the bare id if that load fails. `job_new_bv_config.html` offers this as a `<datalist>` alongside its free-text id field (bv-config can still create a brand-new id, so the field stays free text - the list is a suggestion, not a constraint); `job_new_bv_gps.html` uses a `<select>` instead, since bv-gps only ever works against an already-configured id - if none exist yet, the page points at bv-config instead of showing an empty dropdown. `_find_camera_archive()` (the archive browser's camera-to-archive-path resolution) leans on the exact same `default_config_dir()`.

**`default_config_dir()` in a container**: every `bv-*` CLI's own `--config-dir` flag defaults to `default_config_dir()` (`~/.config/beyond-video`), which works fine for a native/bare-metal install but silently breaks inside `bv-web`'s Docker container - a fresh, empty `$HOME` baked into the image with nothing persisted there, and no per-invocation flag to override it for either the camera pick-list/archive browser or the in-process `start_bv_config()`/`start_bv_gps()` job runner (both deliberately don't take a `--config-dir` override - "curated subset, not every CLI flag"). Confirmed missing on a real deployment: `bv-web`'s container saw zero cameras - empty pick-list, archive browser 404ing every camera id - until this was wired up. Fixed with a `BEYOND_VIDEO_CONFIG_DIR` environment variable `default_config_dir()` checks before falling back to `~/.config/beyond-video`; `docker-compose.yml` sets it to `/data/camera-config` for `bv-web`'s service and mounts the same host folder `bv-cli`'s own `--config-dir /data/config` invocations already write into, so a camera set up either way is visible to both. No change needed to `bv-web`'s own CLI surface or `create_app()`'s signature - the override lives entirely in `default_config_dir()` itself.

*(Later superseded: the no-override fallback moved from `~/.config/beyond-video` to `~/beyond-video-data/.config`, with a one-time auto-migration of any existing folder - see `default_config_dir()`'s own docstring and `WORKING_CONTEXT.md`. Docker deployments are unaffected, since `BEYOND_VIDEO_CONFIG_DIR` always wins before that fallback is even considered.)*

**The archive-browser mount, separately from the config mount above**: fixing `default_config_dir()` above made `bv-web` see cameras again, but the archive browser (`/archive` routes) reads a camera's *recordings* from `CameraConfig.archive` (e.g. `/data/archive/Kirby`), not from `default_config_dir()` - a second, independent path that also needs to resolve to something real inside the container. `docker-compose.yml`'s `bv-web` service didn't mount `/data/archive` at all until this was noticed (Christer's own report after the config fix: "No recordings found in this camera's archive yet." on every camera, even ones `bv-download` had already filled with files) - only `bv-cli` had it. Fixed by adding the same `./data/archive:/data/archive` mount to `bv-web` (read-only, since the archive browser never writes). If the real archive lives on a different host path (Christer's case: `/volume1/Dashcam/files`, via `docker-compose.override.yml` - see `docs/DEPLOY.md`), that override has to repeat the redirect for `bv-web`'s copy of the mount too, not just `bv-cli`'s - they're two separate `volumes:` entries in two separate services, and compose won't infer one from the other.

**Form layout - Required / Time range / Defaults / Optional, plus help tooltips**: each job form's fields are grouped into up to four `.option-group` sections (a plain `<h3>` heading, no JS) - `Required` for fields with no sensible default (bv-config's camera id, bv-gps's/bv-generate's/bv-export's/bv-download's camera pick-list), an optional `Time range` group placed right after `Required` for commands with `--from`/`--until`/`--timestamp` fields (bv-download's own three time fields, laid out side by side in a `.field-row`, rather than left buried in `Optional` where a first-time visitor might not spot them), `Defaults` for a field that's already filled in with a sane value the owner can still override (bv-gps's/bv-download's `--timeout`; bv-generate's Whisper model size/language hint; bv-export's `--stitch-layout` and every `--stitch-mirror-*`/`--stitch-gsensor-size` flag that ships with a real argparse default), and `Optional` for everything else - an off-by-default toggle (bv-gps's "skip reverse-geocoded address lookup", bv-download's recording-kind checkboxes and `--dry-run`/`--files`/`--verbose`/`--trace` flags, grouped into `.checkbox-row`s rather than one per line) or a flag with no default at all (bv-export's `--prefix`, every render/stitch-panel flag). A command doesn't have to fill all four - bv-config's job form today only has a `Required` group, since its one other real flag (`--config-dir`) is deliberately not exposed (would conflict with the camera-picker's assumption of a single `default_config_dir()`). This grouping turned out to scale cleanly all the way up to bv-export's own ~44 flags (see "Curated subset vs. full parity" above) - it's just a much longer `Optional` section, not a different layout. Each field also gets a small circular "?" - a CSS-only tooltip (`.help-tip`/`.tooltip-text`, shown on hover or keyboard focus, no JavaScript) explaining what it does in a sentence or two, plus a `.command-help` box at the top of the page explaining what the command as a whole does.

## Structure

```
src/blackvue/web/
    app.py        FastAPI app factory (create_app()) - routes, the
                   HTTPException handler that turns a 401 into a redirect
                   to /login and a 403 into a rendered "forbidden" page.
    auth.py        SessionStore (in-memory session-id -> username map,
                   not a signed cookie/JWT - see its own docstring for the
                   restart-loses-sessions trade-off this accepts), plus the
                   require_login/require_owner FastAPI dependencies routes
                   use to gate access.
    users.py        User accounts: username, PBKDF2-HMAC-SHA256 password
                   hash, role. A plain hand-editable TOML file (same pattern
                   as core/camera_config.py), not a database - there are
                   only ever a handful of accounts.
    trips.py        Scans a bv-export --target directory for trip folders -
                   a trip is identified by containing trip.log, the first
                   file export_trip() always writes. Deliberately doesn't
                   touch blackvue.archive/blackvue.trip at all: those model
                   the source recordings before a trip exists as a folder;
                   this only ever looks at bv-export's already-written
                   output.
    archive_browser.py
                   ArchiveRecording wrapper + scan_archive()/
                   find_recording()/group_by_day()/filter_recordings()/
                   kind_options() - browses a camera's raw bv-download
                   archive (CameraConfig.archive), reusing
                   blackvue.archive.Archive/ArchiveReader rather than
                   scanning the filesystem itself, and
                   lexicaltimeparser.py for the time-range filter.
                   filter_recordings() also takes videos_only, hiding
                   recordings whose ArchiveRecording.has_video is False
                   (thumbnail downloaded, video never did) - on by
                   default. The list page's own checkbox is the
                   opt-in "Show all recordings (including ones without
                   video)" (`include_no_video`), not a videos_only
                   checkbox that defaults to checked - see
                   _archive_filter_flags() in app.py for why that
                   framing was chosen (an unchecked checkbox is never
                   actually submitted, so an opt-in that defaults to
                   unchecked needs no extra marker field to tell a
                   fresh page load apart from a real submission).
                   find_recording() uses ArchiveReader's targeted
                   read_recording() rather than a full scan - see
                   "Archive browser" above for why that matters.
                   ArchiveRecordingCache wraps find_recording() with a
                   short TTL, same pattern as trips.py's TripCache -
                   the detail page/thumbnail/file-serving routes all
                   resolve the same recording through it rather than
                   re-scanning per request. Those same routes also
                   resolve a camera id to its archive path via
                   core/camera_config.py's CameraConfigCache (same
                   short-TTL pattern again) instead of re-reading and
                   re-parsing that camera's .cfg on every request -
                   see that class's own docstring for why it lives in
                   core/ rather than here, unlike the other two
                   caches.
    jobs.py         JobRunner/Job/JobStatus - runs bv-config/bv-gps/
                   bv-generate/bv-export/bv-download/bv-ls/bv-scribe/
                   bv-search as background threads (in-process, not
                   subprocesses) and tracks each one's output/status/
                   pending-prompt. Also BvExportArgError,
                   raised by start_bv_export() when bv-export's own
                   parse_args() rejects the web form's argv.
                   start_bv_download() has no equivalent exception - it
                   always forces --yes into its own argv, so bv-download's
                   parse_args() never has a reason to reject it.
                   start_bv_ls() also has none - its two numeric fields are
                   cleaned to int-or-None in app.py's own route before this
                   is ever called. start_bv_scribe()/start_bv_search() have
                   none either - bv_scribe.py/bv_search.py already had
                   injectable say/warn from their original build, so no
                   refactor was needed here, and bv-search's own
                   at-least-one-of-text/near/place pre-check happens in
                   app.py's route, before start_bv_search() is ever called.
                   See "Job runner" above.
    templates/      Server-rendered Jinja2 templates (base/login/welcome/
                   trip_list/trip_detail/archive_camera_list/
                   archive_recording_list/archive_recording_detail/
                   forbidden/job_new_bv_config/job_new_bv_gps/
                   job_new_bv_generate/job_new_bv_export/
                   job_new_bv_download/job_new_bv_ls/job_new_bv_scribe/
                   job_new_bv_search/job_detail) - no
                   client-side app to build, no JSON API; the job_detail
                   page polls via a <meta refresh>, not a websocket (see
                   "Job runner" above for its ?paused=1 escape hatch).
                   welcome.html is the post-login landing page (GET /) -
                   see "What it does today" above.
    static/
        backgrounds/  bg-light.jpg/bg-dark.jpg - the two theme background
                   images (see "Theme" above), pre-downscaled/re-encoded
                   to a web-appropriate size rather than shipping the
                   much larger PNG originals. Listed in pyproject.toml's
                   [tool.setuptools.package-data] (same lesson as
                   templates/*.html above) and served via a StaticFiles
                   mount app.py adds at /static.
```

`cli/bv_web.py` is the actual entry point (`bv-web` in `pyproject.toml`'s `[project.scripts]`), with two subcommands: `bv-web serve` (run the app against a `--target` directory and a users file) and `bv-web adduser` (create/update an account without needing the app itself running).

## Relationship to bv-live

`bv-live` - documented in full in `docs/ARCHITECTURE.md` - is the one piece that touches both projects. It shares `bv-web`'s `web` dependency extra in `pyproject.toml` ("bv-live shares this group rather than getting its own: it needs the exact same fastapi/uvicorn stack, just for a different app"), but it is not part of `blackvue.web` - it's its own top-level package, `blackvue.live`, with no login, no accounts, no session store, and no connection to `bv-export`'s trip folders at all. It talks directly to the camera's own live feed instead. Don't confuse "shares a dependency group with bv-web" with "is part of bv-web" - the two are related only by that one shared Python dependency, not by shared code, data, or purpose.

## Deployment

`bv-web` is the piece of this project actually meant to run always-on, reachable by more than one person - see `docs/DEPLOY.md` for the concrete Synology NAS setup: its own `Dockerfile`, its own entry in `docker-compose.yml`, a mounted `--target` directory (the same one `bv-export` writes to, wherever that happens to run), and a mounted users file. The heavier pipeline steps (`bv-generate --transcribe`, `bv-export`'s own rendering) can run on the NAS too via the separate `Dockerfile.cli`/`bv-cli` image, or faster on a PC with a GPU - either way, `bv-web` itself only ever needs read access to whatever `--target` directory ends up on the NAS.
