# bv-web architecture (side project)

`bv-web` is a small, separate side project from the main `bv-*` pipeline documented in `docs/ARCHITECTURE.md`: a login-protected web app for *browsing and watching* trips the pipeline's `bv-export` step already produced. It doesn't download from a camera and doesn't generate anything - but it does read the raw source archive too, via the archive browser (see "Archive browser" below), in addition to `bv-export --target`'s own output folders. That means it needs both `data/trips` and `data/archive` mounted in deployment (see "Deployment" below) - an easy thing to miss since only the trips mount was needed in this project's earlier increments. For the one piece that crosses over between the two projects, see "Relationship to bv-live" below.

## Why it's a separate project, not a feature of the pipeline

The pipeline (`bv-config` through `bv-export`, plus `bv-live`) is built to be run by one person, from their own machine, with no login at all. `bv-web` exists for a different situation entirely: letting other people - family members, say - see trips after the fact, from a browser, without shell access to the machine that ran the pipeline. That needs accounts, roles, and sessions, none of which the rest of the project has any use for - keeping it a separate top-level package (`blackvue.web`, not folded into `blackvue.export`/`blackvue.cli`) means none of that login machinery leaks into tools that were never meant to need it.

It also has its own, heavier optional-dependency group (`fastapi`, `uvicorn`, `python-multipart`, `Jinja2` - see `pyproject.toml`'s `web` extra) and, in deployment, its own Docker image (`Dockerfile`) separate from the pipeline's own (`Dockerfile.cli`) - see "Deployment" below.

## What it does today

Started as deliberately browse/watch only; later increments (below) added the ability for the owner to trigger every `bv-*` pipeline command - `bv-config`, `bv-gps`, `bv-download`, `bv-generate`, `bv-export`, and `bv-ls` - from the browser. `bv-ls` was the last one wired in, and also the odd one out chronologically: it's the very first `bv-*` command this project ever had, overlooked in every earlier round of "wire the pipeline into the browser" until Christer pointed out the gap. See "Job runner" below for its own design notes.

- **Login** - username/password, session cookie. Two roles: `owner` (currently just Christer) and `viewer` (everyone else). Browsing/watching trips and the raw archive works the same for both roles; triggering a job (below) is `owner`-only.
- **Welcome page** (`GET /`) - the actual post-login landing page, added after Christer's own feedback that trips shouldn't be the first thing a user sees: "I don't think we should start with trips after login, yes trips are the end goal, but not the starting." A short "Welcome to Beyond Video" heading/summary plus a `Home`/`Trips`/`Browse archive` (and, for the owner, every job-trigger) quick-link grid - `welcome.html`, gated by `require_login` like everything else here, not `require_owner`, since a viewer should land somewhere too, not just the owner. This page also turns its own background tint *and* blur off entirely (`.page-tint--none`/`.page-bg--sharp`, see "Theme" below) - Christer's own suggestion, "we could also make the background totally untinted for this page" - rather than reusing the same dark, blurred backdrop every other page keeps for legibility over its own denser table/panel content. The blur turned out to matter as much as the tint: an initial tint-only version still "look[ed] tinted" to Christer even with the dark wash genuinely off, because `.page-bg`'s existing `filter: blur(18px)` alone was already enough to read as flat/washed-out - see "Theme" below for both overrides together.
- **Trip list** (`GET /trips`, moved off `GET /` for the welcome page above) - every trip folder under the configured `--target` directory, scanned fresh on every request (not cached), so a trip `bv-export` finishes writing while `bv-web` is already running shows up without a restart.
- **Trip detail** - video playback (range-request support comes for free from Starlette's own `FileResponse`, so seeking/scrubbing works), plus GPX/SRT/LRC download links, whichever of those a given trip actually has (a trip only has the files the `bv-export` run that produced it actually asked for - no `map.mp4` without `--map`, etc.). A video player issues one HTTP request per range while seeking/buffering, and each one resolves the same `trip_id` again - `trips.TripCache` (a small per-trip, short-TTL cache, default 2 seconds) sits behind that resolution so a burst of range requests from one seek/buffer event collapses into a single real `scan_trip()` call instead of repeating its ~nine stat()/open() calls every time. Deliberately scoped to this single-trip lookup only - the trip list below still scans fresh on every request, unaffected.
- **Archive browser** - the raw per-camera archive `bv-download` actually writes to disk, before `bv-export` groups anything into trips: a camera picker, a day-grouped thumbnail grid per camera, and a per-recording detail page. See "Archive browser" below for how.
- **Jobs (owner-only)** - the owner can trigger `bv-config` (set up or edit a camera), `bv-gps` (get a live GPS fix, against an already-configured camera id only), `bv-download` (download recordings from the camera into its archive), `bv-generate` (extract audio/duration/transcript/translation for a camera's archive), `bv-export` (detect trips and export them), `bv-ls` (print a camera's archive as a compact table, or one row per detected trip), `bv-scribe` (describe scenes and/or read visible text via a vision-language model), or `bv-search` (search transcripts/translations/scene descriptions by text and/or GPS proximity) as a background job from the browser, watch its output, answer `bv-config`'s wizard questions as they come up, and cancel a job that's running or stuck. See "Job runner" below for how.
- **Theme** - a manual light/dark toggle (a `bv_theme` cookie, read directly in `base.html` via `request.cookies` rather than every route threading a theme variable through its own `TemplateResponse` context), and a full-app background image behind every page: two fixed, full-viewport layers (`.page-bg` - the theme's own photo, blurred; `.page-tint` - a flat wash of the theme's `--bg` color at partial opacity over it) sit behind the real page content (now a `.page-shell` div, not `<body>` itself), swapped per-theme the same way every other CSS custom property in `base.html` is. Christer's own two derived aerial-city renders (see `WORKING_CONTEXT.md` for how the dark one was color-remapped from the light one specifically, to keep them a true matched pair) - shipped as `web/static/backgrounds/bg-light.jpg`/`bg-dark.jpg`, served through a plain unauthenticated `StaticFiles` mount at `/static` (cosmetic images, not trip data, so no login check needed - unlike every other file-serving route in this app). `.page-tint` also has a per-page opt-out: `base.html`'s tint `<div>` reads its class from a `{% block page_tint_class %}{% endblock %}`, empty by default, so every existing template's tint is untouched; `welcome.html` overrides it (`page_tint_class` -> `page-tint--none`, a plain `opacity: 0`) to show the background photo at full strength on the page that wants it. Not a reusable opacity variable - there's only a couple of pages that need this today, and "off" is a much simpler thing to reason about than "some other number." `.page-bg` got the identical treatment for the same reason, one round later: turning the tint off wasn't actually enough on its own - Christer's "It look tinted to me" after seeing the first version turned out to be the `18px` blur itself reading as flat/washed-out with no color overlay left to blame it on. `{% block page_bg_class %}{% endblock %}` -> `page-bg--sharp` (`filter: none; transform: none` - the `scale(1.1)` only ever existed to hide the blur's own edge fringe, so it drops too) is `welcome.html`'s second override. `login.html` followed the same route right after, per Christer's "the login page should also have an untinted background" - it fills the identical `page_bg_class`/`page_tint_class` blocks welcome.html does.

**Legibility over an untinted photo went through three attempts before it actually worked.** Losing both the tint and the blur left the header title, nav tabs, `welcome.html`'s hero heading/summary, and `login.html`'s field labels sitting directly on a genuinely busy photo (dense rooftops/streets, high-frequency detail everywhere) with nothing behind them - first tried a `text-shadow` on the hero copy alone, then extended and strengthened the same shadow to cover the header/tabs/labels too via a `.page-tint--none ~ .page-shell ...` sibling-combinator selector (scoped so it only ever fires on a page that's turned its own tint off). Both rounds still came back from Christer as genuinely hard to read, screenshot in hand each time - a shadow's small blur radius just can't guarantee contrast against real photographic detail the way it can against a flat color; it wins locally, not everywhere text might land. The actual fix: give the header, `.tabs`, `.login-box`, `welcome.html`'s hero card, and its `.quick-links-group-label` chips a small translucent surface to sit on instead - `background: rgba(var(--bg-rgb), 0.78)` plus `backdrop-filter: blur(14px)` (a frosted-glass panel, the same idea a native app's floating toolbar uses over content), replacing the shadow rules entirely rather than stacking on top of them. Deliberately not the same thing as the page-wide `.page-tint` Christer asked to remove: the tint washed the *entire* photo at all times; these panels cover only the handful of small regions that actually hold text (a toolbar strip, a couple of cards), leaving the rest of the photo - most of the page - fully exposed at full clarity. Still scoped through the same `.page-tint--none ~ .page-shell` sibling combinator, so it only ever applies to a page that's opted into the untinted background; every other page's header/nav/panels are completely untouched.

## Archive browser

Trips only exist once `bv-export` has processed them; the archive browser shows what's on disk before that - every raw recording `bv-download` has already saved for a camera, with a thumbnail per recording so a long archive is easy to scan visually. `web/archive_browser.py` (`ArchiveRecording`, `scan_archive()`, `find_recording()`, `group_by_day()`) is deliberately thin, the same way `trips.py` is thin: it reuses `blackvue.archive.Archive`/`ArchiveReader` - the exact same reader `bv-ls`/`bv-export` already use to enumerate recordings from a flat, unstructured archive directory - rather than adding any new disk-scanning logic of its own.

A camera id in a URL (`/archive/{camera_id}`) is resolved to its archive directory via `CameraConfig.archive` - the directory `bv-download` writes raw recordings to. This is a different directory from `bv-export --target`/`app.state.target` (the trips directory `trips.py` reads) - a camera id names a *source* archive, a trip id names *processed* output. Don't confuse the two; `app.py`'s `_find_camera_archive()` helper is the only place this resolution happens, precisely to avoid that mix-up spreading across routes.

The camera list (`/archive`) reuses `_camera_options()` - the same pick-list `bv-config`/`bv-gps`'s job forms already build (see "Camera pick-list" below). The per-camera page (`/archive/{camera_id}`) groups recordings by calendar day, newest day and newest recording first, and shows each recording's thumbnail if it has one - real `.thm` files `bv-download` already downloads (see the sidecar-probing feature in `WORKING_CONTEXT.md`), preferring front, then rear, then interior. A recording with no thumbnail at all (an older archive, or a camera/firmware that doesn't serve `.thm` files) shows a plain "No thumbnail" placeholder instead of breaking the grid - thumbnail presence was never guaranteed, and there's no ffmpeg-based thumbnail generation anywhere in this project to fall back to. The detail page (`/archive/{camera_id}/{recording_id}`) plays the recording's best available video and links every video file it actually has (front/rear/interior). It doesn't link the GPS/g-sensor sidecar files - `.gps`/`.3gf` have no browser-recognized MIME type, so `FileResponse` would just trigger a download rather than displaying anything, and Christer didn't want them shown at all. `ArchiveRecording.sidecars`/`has_gps`/`has_gsensor` still exist on the model (and are still tested) for any future caller that wants them; the detail template simply doesn't render that loop.

Two file-serving routes (`/archive/{camera_id}/{recording_id}/thumbnail/{direction}`, `/archive/{camera_id}/{recording_id}/files/{filename}`) follow the same allow-list pattern `trips.py`'s `trip_file` route already established: `ArchiveRecording.known_filenames` is the frozenset of real filenames a recording actually owns, checked before ever touching the filesystem, and `camera_id`/`recording_id` path segments are rejected outright if they contain `/`, `\`, or a `.`/`..` segment - the same guard `_find_trip()` applies to `trip_id`.

**Per-recording lookups don't scan the whole archive.** `find_recording()` is called once per thumbnail on the grid page and once per HTTP range request a video player makes while seeking/buffering - both happen many times per page view/playback session. It resolves a recording via `ArchiveReader.read_recording()` (a targeted glob for just that recording id's own files) rather than `scan_archive()`'s full directory read, which would otherwise stat() every file across the whole archive on every single one of those calls - an N-thumbnail page load would be O(N^2), and a video player would re-scan the whole archive on every range request, which is exactly what made both feel slow/hung on a real archive with hundreds of recordings. `scan_archive()` itself (used once per page load, to build the day-grouped grid) is still a full read - that's a single, unavoidable O(archive size) cost per page, not per recording.

**Filtering** (mode + lexical time range): a long archive can have thousands of recordings, so `/archive/{camera_id}` also accepts filter query params - `mode` (repeatable, N/E/M/P/A), plus `timestamp`/`from`/`until`. The time filter reuses `LexicalTimeParser`/`TimeInterval` from `lexicaltimeparser.py` - the same lexical-prefix matcher `bv-ls`/`bv-export`/`bv-download`/`bv-generate` already filter recordings with on the CLI side (a prefix like `2026`, `20260715`, or `20260715_14` expands to an inclusive range; `--timestamp` can't be combined with `--from`/`--until`). `archive_browser.filter_recordings()` applies both filters together over an already-scanned list; `kind_options()` is the canonical N/E/M/P/A list the filter bar's checkboxes are built from. No mode checked means no mode filter (show every kind) - `app.py`'s route turns an empty checkbox selection into `modes=None` rather than `modes=set()`, since the latter would mean "match nothing." A bad/conflicting time filter shows the unfiltered list plus an error message rather than a 500 or a silently-ignored filter. The filter bar is a plain `GET` form (bookmarkable/shareable URL, no JS) rendered above the thumbnail grid on `archive_recording_list.html`.

Access is `require_login` (any logged-in user), the same as trip browsing - not `require_owner` like the job-trigger routes. No caching here: every request rescans the archive directory fresh (unlike `trips.py`'s single-trip lookup, which now goes through `TripCache` - see "Trip detail" above; the two aren't the same shape of problem - the archive browser was fixed by *avoiding* a full-archive scan per request via a targeted lookup, since scanning here really does mean touching every recording; `trips.py`'s `scan_trip()` was already a targeted single-folder read, just an uncached one, since there's no full-directory cost to avoid in the first place).

**Parking-mode video playback.** Every Parking (`P`) recording's own MP4 fails ffmpeg's/browsers' strict container validation outright ("contradictionary STSC and STCO" - a known BlackVue quirk, not per-file corruption; see `WORKING_CONTEXT.md`'s "Correction: the ffprobe failures aren't per-file corruption" entry), which used to make these recordings silently fail to play in the archive browser's `<video>` tag - Christer's own report: "bv-web can't play parking videos, probably because it's a timelapse video." Root cause turned out to be narrower than the timelapse frame rate: confirmed against one of Christer's own real recordings (via `scripts/dump_parking_container.py`) that the video track's own sample tables are completely intact, and the fault is an empty, vestigial audio track (zero samples, zero chunks, but a stray table entry anyway) - exactly the shape `generate/mp4_box_reader.py`'s own docstring had already theorized. `generate/mp4_repair.py`'s `repair_parking_container()` drops just that one broken audio track from a copy of the file's `moov` box, leaving the video track and all of `mdat` (the real frame data) byte-for-byte untouched; `load_or_repair_parking_video()` wraps it in the same load-if-cached-else-compute-and-cache pattern as the OSM road/geocode caches, writing repaired copies under `default_config_dir() / ".parking_repair_cache"` (bv-web's own writable scratch space, not the archive itself, for the same read-only-mount reason the geocode cache moved there - see "Fix geocode cache dir" in `WORKING_CONTEXT.md`). The `/archive/{camera_id}/{recording_id}/files/{filename}` route swaps in the repaired copy transparently for a Parking recording's own video files only, falling back to the original file unchanged for anything outside that one confirmed, narrow pattern - no template or URL changes needed, since the `<video>` tag's `src` never changes.

## Job runner

`bv-config`'s wizard needs to ask questions back, and any of the wired-in commands can run for a while (`bv-export`'s own rendering especially, `bv-download` on a large range) - neither fits the request/response shape of an ordinary route. `web/jobs.py` (`JobRunner`, `Job`, `JobStatus`) runs each triggered command in a background `threading.Thread`, **in-process, not a subprocess**: the job runner calls the target CLI module's own already-tested `_run()` function directly (`cli/bv_config.py`, `cli/bv_gps.py`, `cli/bv_download.py`, `cli/bv_generate.py`, `cli/bv_export.py`, `cli/bv_ls.py`, `cli/bv_scribe.py`, `cli/bv_search.py`), passing it `ask`/`say`/`warn` callables that write into that job's own `Job.output` list instead of a real terminal.

This sidesteps a real problem a subprocess approach would have: a subprocess's stdout can't reliably tell "waiting for input" apart from "more output is still coming", since `input()`'s own prompt text has no trailing newline - scraping raw bytes for that would need fragile heuristics. Calling the real Python function directly means the job runner controls exactly when `ask()`/`say()` fire, no scraping needed. It also means each job's `ask`/`say` closures only ever touch that one job's own output list, not the real process-wide `sys.stdout` - safe for jobs to run concurrently without a global-redirect hazard.

`bv-config`'s `prompt()`/`edit_endpoints()`/`run_wizard()`/`_run()`, `bv-gps`'s `_run()`, `bv-generate`'s `_run()` (and every internal helper it calls - not just the top-level function, since `bv-generate`'s own tests call several of those helpers directly without passing `say`/`warn`, so they all needed real-`print` defaults too), `bv-export`'s `_run()`, and `bv-download`'s `_run()`/`_capture_record_time()` all gained injectable `ask`/`say`/`warn` keyword-only parameters for this, defaulting to the real `input`/`print`/stderr-`print` - real terminal use is unaffected. `bv-ls`'s own `print_trips()`/`bv_ls()`/`_run()` got the same treatment, but with only `say` - it has no warnings or prompts of its own, so there's no `ask`/`warn` to thread through. `bv-scribe`'s and `bv-search`'s own `_run()`s already had injectable `say`/`warn` keyword-only parameters from when they were originally built (see their own `WORKING_CONTEXT.md` entries), so wiring them into the job runner needed no CLI-side refactor at all - `start_bv_scribe()`/`start_bv_search()` below could be added directly. That refactor also had to fix a real formatting hazard: `bv-ls`'s grouped (non-`--trips`) table used to build each header/data row across several `print(..., end=...)` calls rather than one call per line, which doesn't survive a `say` that appends one complete `Job.output` entry per call - each row is now assembled as a plain string first and handed to `say` once, byte-for-byte the same printed result, just built differently. When `ask()` is called, the job's status flips to `waiting_for_input`, the prompt text is recorded on the `Job`, and the call blocks on a `queue.Queue` until the browser POSTs an answer (`Job.submit_answer()`); the job page (`templates/job_detail.html`) shows a form for that prompt and polls via `<meta http-equiv="refresh" content="2">` rather than a websocket - no client-side JS, consistent with the rest of `bv-web`'s server-rendered approach. The refresh only fires while `status == "running"` - it's suppressed once a job reaches `waiting_for_input` (and once it's finished), since a timed reload while the owner is mid-answer would wipe whatever they'd typed into the answer field before they could submit it; the page instead only reloads again once the owner's own `POST /jobs/{job_id}/answer` redirects back. It's also suppressed by a `?paused=1` query param the job page's own "Pause auto-refresh" link sets - added after Christer hit a real problem reading a long job's output: every 2-second reload is a full page load, which always snaps scroll back to the top, so reading anything above the very bottom of a still-running job's transcript kept getting yanked out from under him. Pausing freezes the page on its current snapshot (a plain link toggle, not JS, the same server-rendered pattern the archive browser's own filters use); a "Resume auto-refresh" link drops the param again. Jobs are held in an in-memory `dict` on `JobRunner` - the same restart-loses-state trade-off `SessionStore` already accepts (a job mid-run doesn't survive a restart regardless of whether it's tracked).

**`bv-download`'s own wrinkle: a real interactive prompt that must never actually run here.** Unlike `bv-config` (built around `ask()` throughout its wizard), `bv-download` has exactly one interactive moment - `confirm()`'s plain `input()` call, gated behind `sys.stdin.isatty() and sys.stdout.isatty()` - and it was never converted to go through `ask()`, because there was no need to: `start_bv_download()` always appends `--yes` to the argv it builds, regardless of what the web form said, so `confirm()` is never reached from a job. This isn't just belt-and-suspenders around the tty check (which would likely already be `False` inside a backgrounded web-server process) - it's the only safe option, since `confirm()`'s `input()` reads the real process stdin, which this job runner has no way to answer through its own `ask()`/`Job.submit_answer()` mechanism. A stray real-stdin block here would hang the job forever with no way for the browser to unblock it, unlike `bv-config`'s wizard, which is built around exactly that kind of exchange. `--host`/`--target`/`--config-dir` are also not exposed on the web form, for the same "curated, not an arbitrary-connection escape hatch" reasoning `bv-gps`'s own omitted `--host` already established - `start_bv_download()` only ever takes an already-configured camera id. One more small deliberate gap: `--trace`'s progress dots print straight to real stdout, not through `say()` - a partial-line, no-trailing-newline stream has no sensible representation in `Job.output`'s list-of-complete-lines shape, so a `--trace` job's dots land in `bv-web`'s own process console/log instead of the job's browser-visible output, same as any other `--trace` run whose stdout isn't a live terminal.

`bv-gps`'s job trigger only accepts an already-configured camera id, not its CLI's own `--host` option - `--host` is a terminal-only "probe a bare IP that hasn't been set up with bv-config yet" escape hatch, not something the browser-facing job form should expose. `bv-generate`/`bv-export`'s job triggers resolve their camera's archive path the same way the archive browser does (`app.py`'s `_find_camera_archive()`), rather than taking a raw path from the form. `bv-scribe`/`bv-search` follow the exact same `_find_camera_archive()` resolution - "you can use the camera id just like the others" was Christer's own framing for wiring them in. `bv-download` is different again: its own positional CLI argument already *is* the camera id (not a bare archive path), so `start_bv_download()` doesn't call `_find_camera_archive()` at all - it just passes the id straight through in the argv it builds, the same shape `start_bv_gps()` already uses, and lets `bv_download._run()` do its own config lookup exactly as a real terminal invocation would.

**bv-export's `_run()` and its own real `SystemExit`**: unlike the other three commands, `bv_export()` (the function `bv-export`'s CLI has always called) legitimately raises `SystemExit` itself in two places (an empty `--duration-heal-archive` request, a bad `LexicalTimeParser` value) - a tested public contract (`test_bv_export.py` asserts `pytest.raises(SystemExit)` around a real call), so it couldn't just be converted to a `warn()` + return like an ordinary error. The new `bv_export._run()` wrapper (used by both `main()` and the job runner, mirroring every other bv-* command's own `_run()` shape) catches that `SystemExit` at exactly that one call site and turns it into `warn(str(exc)) + return 1` instead - `bv_export()` itself keeps raising exactly as it always did, so its existing test contract is untouched. `JobRunner._spawn()`'s own completion handler additionally catches `SystemExit` alongside the usual `Exception` as defense in depth (`SystemExit` subclasses `BaseException`, not `Exception`, so a bare `except Exception` would silently miss one and leave a job stuck showing `running` forever) - not a substitute for handling it at the source, since none of this project's own `_run()`s should ever actually let one escape that far.

**bv-export's `parse_args()` extraction**: `bv-export`'s argument parser used to be built inline inside `main()`, with no reusable way to turn a web form's own argv into parsed `args` the way `bv-config`/`bv-gps`/`bv-generate` already could via their own standalone `parse_args()` functions. Pulled out into its own `bv_export.parse_args(argv)` - the identical `parse_args()`/`main()` split every other bv-* CLI already uses - purely mechanical (`main()` now just calls it), confirmed by the existing 109-test suite passing unchanged.

**Cancellation** (`Job.cancel()`/`JobRunner.cancel()`, a "Cancel job" button on `job_detail.html` whenever a job isn't finished) is honest about what Python can and can't do to a running thread. A job currently `waiting_for_input` is unblocked immediately: `cancel()` pushes a sentinel onto the job's own answer queue, `ask()` recognizes it and raises `_JobCancelled`, which unwinds `_run()` right away - the same as any other exception escaping it. A job that's `running` with no prompt open (e.g. `bv-gps` blocked inside a socket call) can't be interrupted mid-call - `cancel()` instead flips the job's status to `CANCELLED` immediately so the browser stops trusting its output, while the background thread itself may keep running invisibly (it's a daemon thread, so it can't block process shutdown either way) until whatever it's blocked on returns or times out on its own; `JobRunner._spawn()`'s completion handler checks for this and won't overwrite an already-`CANCELLED` status with a stale success/failure result if the thread does eventually finish.

All job routes (`GET`/`POST /jobs/bv-config`, `GET`/`POST /jobs/bv-gps`, `GET`/`POST /jobs/bv-download`, `GET`/`POST /jobs/bv-generate`, `GET`/`POST /jobs/bv-export`, `GET`/`POST /jobs/bv-ls`, `GET`/`POST /jobs/bv-scribe`, `GET`/`POST /jobs/bv-search`, `GET /jobs/{job_id}`, `POST /jobs/{job_id}/answer`, `POST /jobs/{job_id}/cancel`) are gated by the existing `require_owner` dependency rather than a granular per-command permission system - simpler, and there's currently no real semi-trusted third party that would need finer-grained access.

**`Job.replicate_command`**: every `start_bv_*()` method also builds the equivalent real `bv-*` CLI invocation and stores it on the `Job`, shown on `job_detail.html` with a "Copy" button (Christer: "Is it possible for every bv-* command to print out how its called in bv-web, so i can replicate it in pwsh or bash later?"). Built from the exact `argv` each method already assembles for its own `parse_args()` call, with one deliberate substitution: the archive-scoped commands (`bv-ls`/`bv-generate`/`bv-export`/`bv-scribe`/`bv-search`) swap the resolved server-side `archive_path` (e.g. `/data/archive/Kirby`, meaningless outside this container) back out for the plain `camera_id` they were given alongside it - the same id a terminal invocation would use directly, resolved fresh wherever it's pasted as long as that machine also has the camera configured via `bv-config` (Christer's actual dual-machine NAS+PC setup already relies on exactly this). `bv-config`/`bv-gps`/`bv-download` need no substitution, since their own positional argument already *is* the camera id, not a resolved path. `_quote_for_replicate()` wraps a value in double quotes only when it contains whitespace or is empty (e.g. a `--place "Slussen, Stockholm"`) - deliberately not `shlex.quote()`'s single-quote style, which is bash-only and would confuse someone pasting the same line into PowerShell; this is a "good enough for realistic values" convenience, not a fully correct dual-shell quoting implementation (an embedded double quote is escaped with a backslash, which isn't strictly correct PowerShell syntax, but none of this project's own argument values ever contain one). The string also includes whatever flags a job-trigger method always forces on itself (e.g. `bv-download`'s own `--yes`) - it shows what actually ran, not a hypothetical bare terminal command.

**`GET /jobs/{job_id}` sends `Cache-Control: no-store`.** Christer hit a real bug: starting a job, navigating away (e.g. to trigger `bv-ls`), then hitting the browser's Back button showed stale output until he manually reloaded. That's the browser's back/forward cache (bfcache) restoring the exact DOM snapshot from when he left rather than making a new request - the `<meta refresh>` never gets a chance to fire again since no page load happens on Back. `no-store` tells the browser this response can never be served from cache, forcing Back (and any other cached-navigation path) to always re-fetch, so it now shows current status/output the same as a manual reload would.

**Curated subset vs. full parity**: `bv-config`/`bv-gps`/`bv-download` deliberately expose only a curated subset of their own CLI flags (no `--config-dir`, no `--host`/`--target` - see above), each a specific "don't let the web form reach for an arbitrary filesystem/network target" call. Asked how much of `bv-generate`'s and `bv-export`'s own much larger flag surface the web form should expose, Christer's answer was the opposite default: "full parity but grouped by required, default and the rest" - every flag gets its own form field, organized into the same `Required`/`Defaults`/`Optional` groups described below. `start_bv_generate()`/`start_bv_export()` both build a real argv list from their own keyword parameters and run it through the target module's own `parse_args()`, so argparse's own validation (numeric ranges, mutually-exclusive groups, `--stitch-resolution`'s `WIDTHxHEIGHT` shape, and so on) is the single source of truth for what's valid - not re-implemented as a second copy of the same rules in `app.py`. The one deliberate exception, kept from the curated-subset precedent: `bv-export --target` is never a form field at all - `start_bv_export()` always uses `app.state.target`, the exact directory the Trips tab already scans, so a web-triggered export shows up there immediately and the web form can never be pointed at an arbitrary path on the server's filesystem. `bv-download` sits between the two extremes: full parity for its actual download-tuning flags (`--mode`, `--from`/`--until`/`--timestamp`, `--dry-run`, `--files`, `--verbose`, `--trace`), same argv-then-`parse_args()` pattern, but `--host`/`--target`/`--config-dir`/`--yes` are never form fields at all - the first three for the curated-id-only reasoning above, `--yes` because it's always forced on internally instead (see "Job runner" above for why forcing it, not exposing it, is the only safe option). `--files` requires `--dry-run` is `bv-download`'s only cross-field rule, so it gets the same plain `app.py` pre-check `bv-generate`'s own few conditions use, rather than a `BvExportArgError`-style exception built for a much larger validator surface. `bv-ls` lands closest to `bv-generate`/`bv-export`'s full-parity end: every flag its own CLI has gets a form field, since there's nothing destructive or slow about it and no arbitrary-target escape hatch to guard against (unlike `--host`/`--target`/`--config-dir` elsewhere). Its two numeric fields (`--max-gap`/`--gap-tolerance`) are genuinely optional - a blank field means "use `bv-ls`'s own default", not zero - so `app.py`'s route converts a non-blank value with a plain `int(...)` and re-renders the form with a friendly message on `ValueError`, rather than reaching for `BvExportArgError`'s `parse_args()`-`SystemExit`-catching machinery, which would be more indirection than two unconstrained integers need.

`bv-scribe`/`bv-search` both get full parity, like `bv-generate`/`bv-export`/`bv-ls` - but `bv-scribe`'s form uses **progressive disclosure** (the same `<details>`/`<summary>` pattern "Progressive disclosure for the bv-export web form" below established) rather than laying all ~40 flags out flat. First asked, Christer's answer sounded like "curated subset" (leave the zoom-detection/sampling knobs off the form entirely, CLI-only) - that version shipped, then got corrected: "i must have misunderstood Curated subset, i wanted it hidden like in bv-export." The actual ask was progressive disclosure, not omission: every flag still gets a real `JobRunner.start_bv_scribe()` keyword and a real form field, just collapsed by default rather than left off the form. `job_new_bv_scribe.html`'s core (camera id, time range, `--task`/`--camera`/`--model`, the plain on/off flags) stays always-visible; the sampling/model-tuning knobs (`--fps`/`--max-frames`/`--max-pixels`/`--resized-width`/`--resized-height`/`--crop-top`/`--crop-bottom`/`--max-new-tokens`/`--repetition-penalty`/`--no-repeat-ngram-size`/`--do-sample`/`--temperature`/`--top-p`/`--top-k`) live in a collapsed "Advanced sampling & model" `<details>`, the zoom-detection sub-pipeline (`--zoom-signs`/`--zoom-frames`/`--zoom-detect-width`/`--zoom-padding`/`--zoom-ocr-width`/`--zoom-max-new-tokens`/`--zoom-detect-max-new-tokens`/`--zoom-repetition-penalty`/`--zoom-no-repeat-ngram-size`/`--zoom-plate-confidence-check`) live in "Advanced zoom detection", and `--trip-summary-max-new-tokens` lives in "Advanced trip summary" - which auto-opens the moment "Also write a trip summary" is checked, the same one-directional trigger pattern `job_new_bv_export.html`'s own script already uses. `--raw`/`--config-dir` are still not exposed at all (not a disclosure question - they're an escape hatch for non-archive footage with no camera id, orthogonal to this curated-by-camera-id trigger, same as `bv-gps`'s own omitted `--host`), and neither is `--zoom-debug-dir` (a real server-filesystem path, the same "no arbitrary path as a form field" reason `bv-export`'s own `--target` was never a field either). `bv-search`, whose flag surface was always small, gets plain full parity with no disclosure needed: `job_new_bv_search.html` exposes `--text`/`--asset`/`--regex`/`--case-sensitive`, `--near`/`--place`/`--radius`, and `--trace` flat. Both still resolve their camera id to an archive path via `_find_camera_archive()`, the same as every other job trigger - "you can use the camera id just like the others" was the one constraint Christer gave up front. `start_bv_search()`'s route does one small pre-check beyond the plain argv-then-`parse_args()` pattern: at least one of text/near/place must be given (mirroring `bv_search._run()`'s own runtime check, but surfaced as a form re-render with a friendly message rather than a job that immediately fails), and a `--near` value is validated through `bv_search._parse_coordinates()` - the identical helper `bv-search`'s own CLI parser already uses for `--near`'s `type=` - via a function-scoped import, since `app.py` otherwise never imports a `cli.*` module directly at its own module scope (that's `jobs.py`'s job).

**`BvExportArgError`**: `bv-export` has dozens of `type=`/mutually-exclusive-group validators - far more than the other three commands combined - so hand-replicating each one as a separate `app.py` pre-check (the approach `bv-generate`'s own much smaller 3-condition check uses) isn't practical. Instead `start_bv_export()` runs its own `bv_export.parse_args(argv)` call under a synchronous, single-call-scoped `contextlib.redirect_stderr()` and catches the resulting `SystemExit`, re-raising the captured message as `BvExportArgError`. `app.py`'s route catches that and re-renders `job_new_bv_export.html` with the message, the same friendly-error pattern `bv-generate`'s own pre-check uses. This one narrow redirect is safe despite this module's own docstring warning against redirecting real stdout/stderr for a job: that warning is about redirecting *for the duration of a background job* while other jobs may be running concurrently in their own threads; this redirect wraps one plain, synchronous function call, entirely before any `Job` exists or any thread is spawned, so nothing else is running that could be affected by it.

**Camera pick-list**: most people only ever have one camera configured, but nothing stops there being more, so the job-trigger forms don't make the owner remember/retype an id from memory. `core/camera_config.py`'s `list_camera_ids(config_dir)` scans `default_config_dir()` for `*.cfg` files and returns their ids (filenames only - deliberately doesn't parse each file, so one corrupt config can't break the listing). `app.py`'s `_camera_options()` then loads each id's config just to get a friendly `"<name> (<id>)"` label, falling back to the bare id if that load fails. `job_new_bv_config.html` offers this as a `<datalist>` alongside its free-text id field (bv-config can still create a brand-new id, so the field stays free text - the list is a suggestion, not a constraint); `job_new_bv_gps.html` uses a `<select>` instead, since bv-gps only ever works against an already-configured id - if none exist yet, the page points at bv-config instead of showing an empty dropdown. `_find_camera_archive()` (the archive browser's camera-to-archive-path resolution) leans on the exact same `default_config_dir()`.

**`default_config_dir()` in a container**: every `bv-*` CLI's own `--config-dir` flag defaults to `default_config_dir()` (`~/.config/beyond-video`), which works fine for a native/bare-metal install but silently breaks inside `bv-web`'s Docker container - a fresh, empty `$HOME` baked into the image with nothing persisted there, and no per-invocation flag to override it for either the camera pick-list/archive browser or the in-process `start_bv_config()`/`start_bv_gps()` job runner (both deliberately don't take a `--config-dir` override - "curated subset, not every CLI flag"). Confirmed missing on a real deployment: `bv-web`'s container saw zero cameras - empty pick-list, archive browser 404ing every camera id - until this was wired up. Fixed with a `BEYOND_VIDEO_CONFIG_DIR` environment variable `default_config_dir()` checks before falling back to `~/.config/beyond-video`; `docker-compose.yml` sets it to `/data/camera-config` for `bv-web`'s service and mounts the same host folder `bv-cli`'s own `--config-dir /data/config` invocations already write into, so a camera set up either way is visible to both. No change needed to `bv-web`'s own CLI surface or `create_app()`'s signature - the override lives entirely in `default_config_dir()` itself.

**The archive-browser mount, separately from the config mount above**: fixing `default_config_dir()` above made `bv-web` see cameras again, but the archive browser (`/archive` routes) reads a camera's *recordings* from `CameraConfig.archive` (e.g. `/data/archive/Kirby`), not from `default_config_dir()` - a second, independent path that also needs to resolve to something real inside the container. `docker-compose.yml`'s `bv-web` service didn't mount `/data/archive` at all until this was noticed (Christer's own report after the config fix: "No recordings found in this camera's archive yet." on every camera, even ones `bv-download` had already filled with files) - only `bv-cli` had it. Fixed by adding the same `./data/archive:/data/archive` mount to `bv-web` (read-only, since the archive browser never writes). If the real archive lives on a different host path (Christer's case: `/volume1/Dashcam/files`, via `docker-compose.override.yml` - see `docs/DEPLOY.md`), that override has to repeat the redirect for `bv-web`'s copy of the mount too, not just `bv-cli`'s - they're two separate `volumes:` entries in two separate services, and compose won't infer one from the other.

**Form layout - Required / Time range / Defaults / Optional, plus help tooltips**: each job form's fields are grouped into up to four `.option-group` sections (a plain `<h3>` heading, no JS) - `Required` for fields with no sensible default (bv-config's camera id, bv-gps's/bv-generate's/bv-export's/bv-download's camera pick-list), an optional `Time range` group placed right after `Required` for commands with `--from`/`--until`/`--timestamp` fields (bv-download's own three time fields, laid out side by side in a `.field-row`, rather than left buried in `Optional` where a first-time visitor might not spot them), `Defaults` for a field that's already filled in with a sane value the owner can still override (bv-gps's/bv-download's `--timeout`; bv-generate's Whisper model size/language hint; bv-export's `--stitch-layout` and every `--stitch-mirror-*`/`--stitch-gsensor-size` flag that ships with a real argparse default), and `Optional` for everything else - an off-by-default toggle (bv-gps's "skip reverse-geocoded address lookup", bv-download's recording-kind checkboxes and `--dry-run`/`--files`/`--verbose`/`--trace` flags, grouped into `.checkbox-row`s rather than one per line) or a flag with no default at all (bv-export's `--prefix`, every render/stitch-panel flag). A command doesn't have to fill all four - bv-config's job form today only has a `Required` group, since its one other real flag (`--config-dir`) is deliberately not exposed (would conflict with the camera-picker's assumption of a single `default_config_dir()`). This grouping turned out to scale cleanly all the way up to bv-export's own ~44 flags (see "Curated subset vs. full parity" above) - it's just a much longer `Optional` section, not a different layout. Each field also gets a small circular "?" - a CSS-only tooltip (`.help-tip`/`.tooltip-text`, shown on hover or keyboard focus, no JavaScript) explaining what it does in a sentence or two, plus a `.command-help` box at the top of the page explaining what the command as a whole does.

## Structure

```
src/blackvue/web/
    app.py        FastAPI app factory (create_app()) - routes, the
                   HTTPException handler that turns a 401 into a redirect
                   to /login and a 403 into a rendered "forbidden" page.
    auth.py        SessionStore (in-memory session-id -> username map,
                   not a signed cookie/JWT - see its own docstring for the
                   restart-loses-sessions trade-off this accepts), plus the
                   require_login/require_owner FastAPI dependencies routes
                   use to gate access.
    users.py        User accounts: username, PBKDF2-HMAC-SHA256 password
                   hash, role. A plain hand-editable TOML file (same pattern
                   as core/camera_config.py), not a database - there are
                   only ever a handful of accounts.
    trips.py        Scans a bv-export --target directory for trip folders -
                   a trip is identified by containing trip.log, the first
                   file export_trip() always writes. Deliberately doesn't
                   touch blackvue.archive/blackvue.trip at all: those model
                   the source recordings before a trip exists as a folder;
                   this only ever looks at bv-export's already-written
                   output.
    archive_browser.py
                   ArchiveRecording wrapper + scan_archive()/
                   find_recording()/group_by_day()/filter_recordings()/
                   kind_options() - browses a camera's raw bv-download
                   archive (CameraConfig.archive), reusing
                   blackvue.archive.Archive/ArchiveReader rather than
                   scanning the filesystem itself, and
                   lexicaltimeparser.py for the time-range filter.
                   filter_recordings() also takes videos_only, for the
                   list page's "Show only with videos" checkbox - it
                   hides recordings whose ArchiveRecording.has_video is
                   False (thumbnail downloaded, video never did).
                   find_recording() uses ArchiveReader's targeted
                   read_recording() rather than a full scan - see
                   "Archive browser" above for why that matters.
                   ArchiveRecordingCache wraps find_recording() with a
                   short TTL, same pattern as trips.py's TripCache -
                   the detail page/thumbnail/file-serving routes all
                   resolve the same recording through it rather than
                   re-scanning per request. Those same routes also
                   resolve a camera id to its archive path via
                   core/camera_config.py's CameraConfigCache (same
                   short-TTL pattern again) instead of re-reading and
                   re-parsing that camera's .cfg on every request -
                   see that class's own docstring for why it lives in
                   core/ rather than here, unlike the other two
                   caches.
    jobs.py         JobRunner/Job/JobStatus - runs bv-config/bv-gps/
                   bv-generate/bv-export/bv-download/bv-ls/bv-scribe/
                   bv-search as background threads (in-process, not
                   subprocesses) and tracks each one's output/status/
                   pending-prompt. Also BvExportArgError,
                   raised by start_bv_export() when bv-export's own
                   parse_args() rejects the web form's argv.
                   start_bv_download() has no equivalent exception - it
                   always forces --yes into its own argv, so bv-download's
                   parse_args() never has a reason to reject it.
                   start_bv_ls() also has none - its two numeric fields are
                   cleaned to int-or-None in app.py's own route before this
                   is ever called. start_bv_scribe()/start_bv_search() have
                   none either - bv_scribe.py/bv_search.py already had
                   injectable say/warn from their original build, so no
                   refactor was needed here, and bv-search's own
                   at-least-one-of-text/near/place pre-check happens in
                   app.py's route, before start_bv_search() is ever called.
                   See "Job runner" above.
    templates/      Server-rendered Jinja2 templates (base/login/welcome/
                   trip_list/trip_detail/archive_camera_list/
                   archive_recording_list/archive_recording_detail/
                   forbidden/job_new_bv_config/job_new_bv_gps/
                   job_new_bv_generate/job_new_bv_export/
                   job_new_bv_download/job_new_bv_ls/job_new_bv_scribe/
                   job_new_bv_search/job_detail) - no
                   client-side app to build, no JSON API; the job_detail
                   page polls via a <meta refresh>, not a websocket (see
                   "Job runner" above for its ?paused=1 escape hatch).
                   welcome.html is the post-login landing page (GET /) -
                   see "What it does today" above.
    static/
```

`cli/bv_web.py` is the actual entry point (`bv-web` in `pyproject.toml`'s `[project.scripts]`), with two subcommands: `bv-web serve` (run the app against a `--target` directory and a users file) and `bv-web adduser` (create/update an account without needing the app itself running).

## Relationship to bv-live

`bv-live` - documented in full in `docs/ARCHITECTURE.md` - is the one piece that touches both projects. It shares `bv-web`'s `web` dependency extra in `pyproject.toml` ("bv-live shares this group rather than getting its own: it needs the exact same fastapi/uvicorn stack, just for a different app"), but it is not part of `blackvue.web` - it's its own top-level package, `blackvue.live`, with no login, no accounts, no session store, and no connection to `bv-export`'s trip folders at all. It talks directly to the camera's own live feed instead. Don't confuse "shares a dependency group with bv-web" with "is part of bv-web" - the two are related only by that one shared Python dependency, not by shared code, data, or purpose.

## Deployment

`bv-web` is the piece of this project actually meant to run always-on, reachable by more than one person - see `docs/DEPLOY.md` for the concrete Synology NAS setup: its own `Dockerfile`, its own entry in `docker-compose.yml`, a mounted `--target` directory (the same one `bv-export` writes to, wherever that happens to run), and a mounted users file. The heavier pipeline steps (`bv-generate --transcribe`, `bv-export`'s own rendering) can run on the NAS too via the separate `Dockerfile.cli`/`bv-cli` image, or faster on a PC with a GPU - either way, `bv-web` itself only ever needs read access to whatever `--target` directory ends up on the NAS.
